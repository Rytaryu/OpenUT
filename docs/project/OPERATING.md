# 進め方（役割・手順・PR とレビューの決まり）

## 1. 体制

| 役割 | 担当 | 主な成果物 |
|---|---|---|
| PM・PdM（オーケストレーター） | Claude Fable 5.2 | PRD、STATUS、DECISIONS、次の仕事の用意（`backlog`）、判断 |
| 設計 | Claude Fable 5.2（high） | `docs/design/` の設計（構成、状態の遷移、検出の規則、機器との通信の手順、実装計画） |
| 設計レビュー | GPT-6.2 Astra（max） | 設計 PR へのレビューコメント |
| UI/UX デザイン | Claude Opus 5.5（xhigh）。画面のある仕事が出るまで置かない | `docs/design/ui/` の画面設計、操作の流れ |
| 実装 | GPT-6.2 Sol（Ultra） | コード、単体テスト |
| 実装レビュー | Claude Opus 5.5（xhigh） | 実装 PR へのレビューコメント |
| テスター | GPT-6.1 Terra（Ultra。実装担当とは別のタスク） | テスト計画、自動テスト、不具合 Issue |
| オーナー（人間） | Rytaryu | 実機（トラッカー、ドングル、SteamVR）での確認、ログの収集、フィードバック、認証・認可、レポジトリの設定 |

各担当は別々のコンテキストで動く。担当間の受け渡しは、レポジトリのファイル、PR、Issue だけで行う。口頭の前提は存在しない。

## 1.1 依頼を受けて動く運用

実装・テスター・設計・設計レビュー・実装レビュー・UI/UX の各担当は、自分あての依頼が出たときに起動する（イベント起動）。PM は 1 日 1 回（12:35 JST）の定期実行で起動する。依頼は、対象の Issue・PR に相手の `role:*` ラベルを付け、起動用の PR（#1）に `WAKE role:<役割> #<番号>` とコメントして行う。課題や TODO は Issue、やったことの提案は PR で出す。PM はその回で、次の仕事の用意（`backlog` の Issue）、判断、止まっている依頼の起こし直しを行い、最後にオーナーあての進捗報告を書く。PM を待たずに進むよう、承認された PR のマージ、次の仕事（`backlog`）の受け渡し、オーナーの返事の受け渡しは、仕組み（GitHub Actions）が行う（D-15）。手順は `docs/project/roles/README.md` と、役割ごとの手順書（`docs/project/roles/`）にある。全担当を止めるには、main に `docs/project/PAUSED` を置く。

## 2. 作業の流れ

1. PM が依頼を出すか、`backlog` の Issue を用意する（条件がそろうと、仕組みが担当に渡す）。
2. 担当がブランチを切り、作業して PR を作る。PR ごとに CI が動く。
3. レビュー担当が PR にレビューコメントを書く。
4. 作成者が指摘に対応し、対応内容を PR にコメントする。
5. レビュー担当が承認し、CI が通っていれば、仕組み（GitHub Actions）がマージする（条件は `docs/project/roles/README.md` の 6 章）。
6. PM が 1 日 1 回、`docs/project/STATUS.md` を更新する。

## 3. ブランチ

| 種類 | 名前 |
|---|---|
| 設計 | `design/<topic>` |
| UI/UX | `ux/<topic>` |
| 実装 | `feat/<topic>`、`fix/<topic>` |
| テスト | `test/<topic>` |
| 雑務 | `chore/<topic>` |

- `main` は常に動く状態に保つ。文書だけの PR はスカッシュマージ。**コードを含む PR は、履歴を保つ通常のマージ**にする（積み重ねた PR をスカッシュすると、後続の PR が競合するため）。マージ後、後続の PR の base を main に付け替える。
- 1 つの PR は 1 つの目的に絞る。大きい変更は分割する。

## 4. PR の説明の書式

```
## 目的
（どの要件・Issue に対応するか。PRD の番号を書く）

## 変更点
（何をどう変えたか）

## 確認方法
（レビュー担当・テスターが手元で確かめる手順。コマンドを書く。実機に命令を送るコードを含むなら、送る命令をここに列挙する）

## 未解決・判断を仰ぎたい点
（なければ「なし」）

## 次の担当へ
（次に誰が何をすればよいか）

担当: <役割名> (<モデル名>)
```

## 5. レビューの決まり

- すべてのエージェントが同じ GitHub アカウントで動くため、GitHub の承認機能は使えないことがある。レビュー結果は **PR へのコメント**として書き、1 行目を次のどちらかにする。
  - `REVIEW: APPROVE`
  - `REVIEW: REQUEST_CHANGES`
- コメントの末尾に担当名を書く（例: `— 設計レビュー担当 (GPT-6.2 Astra max)`）。
- 指摘は重要度をつける。
  - `[必須]` 直さないとマージできない（誤り、要件の欠落、破綻する設計）
  - `[推奨]` 直したほうがよいが、理由を書けば見送ってよい
  - `[質問]` 意図の確認
- 指摘には、根拠と、できれば代案を書く。好みの問題は書かない。
- レビューの観点
  - 設計: PRD の要件をすべて満たすか。制約（Windows、SteamVR、VIVE Hub と同時に動かせないこと、危険な命令を既定で送らないこと）に合うか。根拠（ログの解析、公開されている解析）と合うか。実装とテストが可能な粒度か。より単純な案がないか。
  - 実装: 設計どおりか。判定ロジックの正しさ。テストの有無と質。公開レポジトリの決まり（`AGENTS.md`）を守っているか。不要な依存。
- `REQUEST_CHANGES` が 2 往復しても収束しないときは、PM が裁定して `DECISIONS.md` に記録する。

## 6. 完了の定義

| 対象 | 完了の条件 |
|---|---|
| 設計 PR | PRD の全要件に対応づけがある。未決事項が列挙されている。設計レビューが APPROVE |
| 実装 PR | CI（ruff、mypy、pytest）が通る。設計との差分が説明されている。実装レビューが APPROVE |
| マイルストーン | テスターの確認が済み、オーナーの実機での確認の手順が `needs-human` の Issue になっていて、その結果が戻っている |

## 7. 人間への依頼

- 人間にしかできない作業は `needs-human` ラベルの Issue にする。
- Issue には、目的、手順（番号つき）、確認してほしい結果、所要時間の目安を書く。
- オーナーの PC とトラッカーが要る作業（実機での確認、ログの収集）は、時間が限られる（平日は夜だけ）。PM は、実機が要る作業と要らない作業を STATUS で分けて管理し、実機の確認はまとめて頼む。
- クラウドで動く担当は、オーナーの PC のログを読めない。ログが要るときは、PM が、オーナーの PC につながった Claude のチャットで、匿名化したものをレポジトリに入れる。

## 8. 記録

- `docs/project/STATUS.md`: 現在地と次の一手。PM だけが更新する。
- `docs/project/DECISIONS.md`: 決定とその理由。PM が main に書く。設計の決定は、設計の PR の説明に「決定の記録（案）」として書かれたものを、その PR が main に入ったあとに PM が書き写す（設計の PR には入れない。設計の PR が `docs/design/` の外を変えると、設計レビューの承認ではマージされないため）。実装の PR の中で決めたことを記録したいときも、PR の説明に書いて PM に渡す。
