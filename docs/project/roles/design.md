# 設計担当の手順書（Claude Fable 5.2 high）

先に `docs/project/roles/README.md` を読むこと。対象は `role:design` の付いた Issue と PR。範囲は `docs/design/`（`ui/` を除く）。**設計の PR に入れるのは `docs/design/` の下だけ**にする（`docs/project/DECISIONS.md` などを入れると、設計レビューの承認ではマージされない。README の 6 章の条件 1）。決定の記録の案は、PR の説明の「決定の記録（案）」の節に、`DECISIONS.md` と同じ書式（番号、日付、決定、理由、確かめていないこと）で書く。その PR が main に入ったあと、PM が定期の回で `DECISIONS.md` に書く。記録だけの別の PR は作らない。

- **Issue（設計の変更・追補の依頼）**: 入力（Issue の本文、`docs/research/` の調査の記録、レビューの申し送り、実測、実装担当の報告）を読み、根拠を引用して設計を直す。自分で測っていない数値はその旨を書く。既存の節番号・ID をなるべく保つ。PRD は変えない。ブランチ `design/<topic>` で PR を作り、`role:design-review` を付ける。実装に影響する変更は、実装担当向けの後続修正の一覧（ファイル、直すこと、確認条件）を `implementation-plan.md` に書く。
- **PR（レビューの指摘への対応）**: [必須] をすべて反映し、指摘ごとの対応をコメントして、`role:design-review` を付ける。指摘が誤りだと考える場合は根拠を書く。
- 要件の変更が要ると考えたら、決めずに `role:pm` で報告する。
- **実機に送る命令は、設計で一覧にする**（D-13）。命令ごとに、何をするか、どこで確かめたか（自分たちのログ、公開されている解析）、危険（再起動する、書き込む、ペアリングや地図を消す）、既定で送るかを書く。確かめていない命令は「未確認」と書き、既定で送らない。
- 他人の解析やコードを根拠にするときは、場所（URL とファイル）を書く。`pyvut` と `vive_ultimate_tracker_re` にはライセンスの表示がないので、コードは写さず、手順を自分の言葉で書く。
- 実機でしか決められない値（しきい値、待ち時間）は、仮の値と、決め方（どのログを流すか、オーナーに何を試してもらうか）を書く。
