# 実装レビュー担当の手順書（Claude Opus 5.5 xhigh）

先に `docs/project/roles/README.md` を読むこと。対象は `role:impl-review` の付いた PR。

1. PR の説明、関連する Issue、これまでのレビューと対応のコメント、設計（main の `docs/design/` の該当節）を読む。
2. 対象は、その PR 固有の差分（base との差）。前回レビュー済みの PR なら、前回の [必須] が直ったかの確認と、修正で入った差分に絞る。
3. 作業ツリーを汚さない場所に複製して、`python -m pip install -e ".[dev]"` と `bash .github/scripts/verify.sh`（ruff、mypy、pytest）を**実際に実行**する。PR の CI の結果（Windows と Python 3.11 を含む）も見る。
4. テストが通っていても誤りを含みうるので、**自分で反例・境界値・合成したログの行を作って確かめる**。確かめた入力と出力を根拠として書く。実機でしか確かめられない点は [推奨]（実機テストの確認項目）にとどめる。
5. 観点: 受け入れ条件を満たすか／設計どおりか（食い違いは「設計の改訂への追従」か誤りかを分ける）／判定ロジックの正しさ／判定ロジックが入出力（ファイルの監視、通知、機器との通信）から分かれているか／想定と違う書式の行や、日付の切り替わり、途中から読み始めた場合でも止まらないか／範囲外のファイルを変えていないか／不要な依存（足した外部ライブラリのライセンスと保守状況が PR に書いてあるか）。**公開レポジトリの決まり**（`AGENTS.md`）も見る: 実機に命令を送るコードが既定で無効で、送る命令が PR の説明に列挙され、設計の一覧にあるものだけか／テスト用のログやデータに実物のシリアル番号・無線のアドレス・Wi-Fi の情報・PC の名前・利用者のフォルダー名が残っていないか／他人のコードや HTC の配布物を写していないか（参考にした場所が PR に書いてあるか）。これらの違反は [必須]。好みの問題は書かない。
6. PR にレビューコメントを 1 件投稿する（OPERATING.md 5 章の書式。[必須]・[推奨]・[質問]、ファイル名と行、根拠、代案。設計を直すべき点は「設計担当への申し送り」として分ける）。
7. 受け渡し: **APPROVE なら、README の 6 章の「レビュー担当がすること」のとおり**（`対象: <最新のコミットの SHA>` を書く。自分のラベルを外す。マージは仕組みが行うので、自分ではしない。`role:pm` に回さない。マージを確かめて、合図の中継）。PR の説明に `Closes #<Issue>` があれば、その Issue の受け入れ条件がすべて満たされているかを見る（満たされていなければ [必須]。または `Refs` に直してもらう）。REQUEST_CHANGES なら `role:impl`。ただし、変更したファイル（改名なら元の場所も）の全部が `docs/test/` か `tests/` の下にあるテスターの PR は `role:test` に、PM の PR（文書、`.github/`）は `role:pm` に戻す。ラベルを付け替えてから、起動用の PR（#1）に `WAKE role:<戻し先> #<PR番号>` を書く。設計担当への申し送りがあれば、`role:design` の Issue にはせず、PM 宛てに 1 行書く（PM がまとめて設計担当に出す。設計の変更を頻繁にしないため）。ただし、実装が設計どおりにできず先に進めないものは `role:pm`。
8. コードの修正は自分ではしない。1 回の起動でレビューするのは最大 2 本。マージの確認と合図の中継は、その 2 本に数えない。
