# 実装レビュー担当の手順書（Claude Opus 5.5 xhigh）

> **移植中（2026-11-27）**: この文書は Rytaryu/OpenUT の進め方を写したもの。ラベルによる受け渡しと自動マージの仕組み（GitHub Actions）は、まだこのレポジトリに入っていない。入るまでは `docs/project/STATUS.md` の「次にやること」に従う。OpenUT 固有の記述が残っていたら、PM が直す。

先に `docs/project/roles/README.md` を読むこと。対象は `role:impl-review` の付いた PR。

1. PR の説明、関連する Issue、これまでのレビューと対応のコメント、設計（main の `docs/design/` の該当節）を読む。
2. 対象は、その PR 固有の差分（base との差）。前回レビュー済みの PR なら、前回の [必須] が直ったかの確認と、修正で入った差分に絞る。
3. 作業ツリーを汚さない場所に複製して、`npm ci`、型検査、lint、層の依存検査、単体テスト、ビルドを**実際に実行**する。
4. テストが通っていても誤りを含みうるので、**自分で反例・境界値・合成信号を作って確かめる**。確かめた入力と出力を根拠として書く。実機でしか確かめられない点は [推奨]（実機テストの確認項目）にとどめる。
5. 観点: 受け入れ条件を満たすか／設計どおりか（食い違いは「設計の改訂への追従」か誤りかを分ける）／判定ロジックの正しさ／16・44.1・48 kHz のどれでも成り立つか（PRD 6.2）／入力の小さい信号でも成り立つか／`domain` が DOM・Web Audio・Node に依存しないか／範囲外のファイルを変えていないか／不要な依存。好みの問題は書かない。
6. PR にレビューコメントを 1 件投稿する（OPERATING.md 5 章の書式。[必須]・[推奨]・[質問]、ファイル名と行、根拠、代案。設計を直すべき点は「設計担当への申し送り」として分ける）。
7. 受け渡し: **APPROVE なら、README の 6 章の「レビュー担当がすること」のとおり**（`対象: <最新のコミットの SHA>` を書く。自分のラベルを外す。マージは仕組みが行うので、自分ではしない。`role:pm` に回さない。マージを確かめて、合図の中継）。PR の説明に `Closes #<Issue>` があれば、その Issue の受け入れ条件がすべて満たされているかを見る（満たされていなければ [必須]。または `Refs` に直してもらう）。REQUEST_CHANGES なら `role:impl`。ただし、変更したファイル（改名なら元の場所も）の全部が `docs/test/` か `tests/e2e/` の下にあるテスターの PR は `role:test` に戻す。ラベルを付け替えてから、起動用の PR（番号は STATUS.md に書く） に `WAKE role:test #<PR番号>` を書く。設計担当への申し送りがあれば、`role:design` の Issue にはせず、PM 宛てに 1 行書く（PM がまとめて設計担当に出す。設計の変更を頻繁にしないため）。ただし、実装が設計どおりにできず先に進めないものは `role:pm`。
8. コードの修正は自分ではしない。1 回の起動でレビューするのは最大 2 本。マージの確認と合図の中継は、その 2 本に数えない。
