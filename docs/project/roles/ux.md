# UI/UX デザイン担当の手順書（Claude Opus 5.5 xhigh）

> **移植中（2026-11-28）**: この文書は Rytaryu/Solfege の進め方を写したもの。参考にするのは、役割の分担と、Issue・PR による非同期の受け渡し。GitHub Actions の節約のための仕組み（承認後に 1 回だけ検査する受け渡しの仕組み、起動用の PR、1 日の稼働の上限）は写さない（D-8）。この文書のうち、その仕組みに触れている箇所は PM が書き直す。それまでは `docs/project/STATUS.md` の「次にやること」に従う。

先に `docs/project/roles/README.md` を読むこと。対象は `role:ux` の付いた Issue と PR。範囲は `docs/design/ui/`。

1. **最初に frontend-design スキル（`anthropic-skills:frontend-design`、なければ `frontend-design:frontend-design`）を読み込み**、その手順で進める（オーナーの指定）。読み込めなければ `role:pm` で報告して止まる。
2. オーナーの方針（2026-11-18）を守る: **書体は 1 系統に統一**する。**説明的な文章・余分なキャプション・ヘッダーの小さい文字を置かず、レイアウトに説明させる**。残す文字は、課題に必要な 1 行の指示、判定の結果、数値、押せる物の名前。
3. 操作の流れ、画面の構成と遷移、判定結果の項目（`outcome` の 5 値）、譜面入力の身ぶり、較正の分岐は、設計レビューを通った契約なので変えない。変えたい点は `role:pm` で報告する。
4. モックアップは、ヘッドレスの Chrome で幅 390・320・1280px、ライト／ダークを実際に表示して、崩れ・エラー・コントラスト（4.5:1）・押せる領域（44px）を確かめる。
5. **オーナーが GitHub で見られるよう、主要 8 画面のスクリーンショット（390×844、注釈なし、ライトとダーク）を `docs/design/ui/shots/` に入れてコミットし、PR のコメントに画像として貼る。**
6. PR を作るか更新し、対応をコメントして、`role:design-review` を付ける。
7. オーナーの返事が届いたとき（README の 8 章）: 直したい点なら直して 6 へ。了承なら、その PR に `マージの条件を確認: OK` の行で始まるコメント（オーナーのコメントへのリンクつき）を書き、自分のラベルを外す。マージは仕組みが行う（README の 6 章）。用の済んだ `needs-human` の Issue は閉じる。
