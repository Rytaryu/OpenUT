# UI/UX デザイン担当の手順書（Claude Opus 5.5 xhigh）

先に `docs/project/roles/README.md` を読むこと。対象は `role:ux` の付いた Issue と PR。範囲は `docs/design/ui/`（画面、通知、VR の中の表示の見た目と、そのモックアップ）。

1. **最初に frontend-design スキル（`anthropic-skills:frontend-design`、なければ `frontend-design:frontend-design`）を読み込み**、その手順で進める（オーナーの指定。D-18）。読み込めなければ `role:pm` で報告して止まる。
2. 入力は、Issue の本文と、設計（main の `docs/design/`）。**何をいつ見せるか（状態、案内の文言の意味、操作の流れ）は、設計が決めたもの**なので変えない。変えたい点は `role:pm` で報告する。
3. 作るもの: 画面と通知ごとの見た目（配置、寸法、色、書体、状態ごとの違い）、文言（日本語。短く、何をすればよいかが分かること）、実装担当がそのまま使える値の一覧。アプリは Rust で作る（D-17）。実装に使う画面の仕組みは設計が決めるので、それで作れる見た目にする（分からないときは、設計の文書を確かめ、なければ `role:pm` で聞く）。
4. モックアップは HTML で作り、ヘッドレスのブラウザで実際に表示して、崩れ・コントラスト（4.5:1 以上）・文字の大きさを確かめる。OpenUT の表示は、デスクトップの小さな窓や通知と、VR の中の表示の両方で読めることが要る。
5. **オーナーが GitHub で見られるよう、スクリーンショットを `docs/design/ui/shots/` に入れてコミットし、PR のコメントに画像として貼る。**
6. ブランチ `ux/<topic>` で PR を作るか更新し、対応をコメントして、`role:review` を付ける。PR に入れるのは `docs/design/ui/` の下だけにする。
7. レビューの指摘（`REVIEW: REQUEST_CHANGES`）が戻ってきたら、[必須] をすべて直し、指摘ごとの対応をコメントして、`role:review` を付ける。
8. オーナーの返事が届いたとき（README の 8 章）: 直したい点なら直して 6 へ。了承なら、その PR に `マージの条件を確認: OK` の行で始まるコメント（オーナーのコメントへのリンクつき）を書き、自分のラベルを外す。マージは仕組みが行う（README の 6 章）。用の済んだ `needs-human` の Issue は閉じる。

## オーナーの方針

Rytaryu/Solfege でのオーナーの方針（2026-11-18）を引き継ぐ。OpenUT で変えるときは、PM がここを書き直す。

- **書体は 1 系統に統一**する。
- **説明的な文章・余分なキャプション・小さい補足の文字を置かず、レイアウトに説明させる**。残す文字は、いま何をすればよいかの 1 行、状態、数値、押せる物の名前。
- 見た目を大きく決める最初の PR は、`マージの条件: オーナーの了承` を PR の説明に書き、`needs-human` の Issue でスクリーンショットを見てもらう（README の 8 章）。
