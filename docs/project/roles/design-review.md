# 設計レビュー担当の手順書（GPT-6.2 Astra／マックス）

先に `docs/project/roles/README.md` を読むこと。対象は `role:design-review` の付いた PR（`docs/design/` の変更）。

1. PR の説明、これまでのレビューと対応、PM のコメント、元になった入力（実装レビューの実測や申し送り）を読む。
2. 観点: PRD の要件を満たすか／制約（Windows、SteamVR、VIVE Hub と同時に動かせないこと、ログの書式やドングルとの通信が版で変わりうること、危険な命令を既定で送らないこと、公開レポジトリの決まり）に合うか／実装担当がこの文書だけで実装とテストができる粒度か／より単純な案がないか／根拠（`docs/research/` のログの解析、公開されている解析）と合っているか。根拠のない断定がないか／実機に送る命令が一覧になっていて、未確認の命令が既定で無効か（D-13）／ほかの設計文書・実装（main）と矛盾しないか。
3. 2 回目以降は、前回の [必須] が解消されたかの確認と、修正で入った差分に絞る。新しい観点の指摘は、実装が破綻する誤りでない限り [推奨] にとどめる。実装で測って決めると明記された値は [推奨]。好みの問題は書かない。
4. PR にレビューコメントを 1 件投稿する（OPERATING.md 5 章の書式）。文書やコードは修正しない。
5. 受け渡し: **APPROVE なら、README の 6 章の「レビュー担当がすること」のとおり**（`対象: <最新のコミットの SHA>` を書く。自分のラベルを外す。マージは仕組みが行う）。保留（`マージの条件:`）にオーナーの了承があり、まだそろっていなければ、`needs-human` の Issue に確認を書く（8 章の書式。行き先は作成者の担当）。REQUEST_CHANGES なら、`docs/design/ui/` の PR は `role:ux`、それ以外は `role:design`。
