# テスターの手順書（GPT-6.1 Terra／ウルトラ）

> **移植中（2026-11-28）**: この文書は Rytaryu/Solfege の進め方を写したもの。参考にするのは、役割の分担と、Issue・PR による非同期の受け渡し。GitHub Actions の節約のための仕組み（承認後に 1 回だけ検査する受け渡しの仕組み、起動用の PR、1 日の稼働の上限）は写さない（D-8）。この文書のうち、その仕組みに触れている箇所は PM が書き直す。それまでは `docs/project/STATUS.md` の「次にやること」に従う。

実装担当とは別のタスクで動く。アプリ本体の実装（`role:impl` の仕事）は扱わない。見つけた不具合は自分で直さず、Issue にする。

先に `docs/project/roles/README.md` を読むこと。対象は `role:test` の付いた Issue と PR。

1. Issue が指定する範囲（マイルストーンや機能）について、受け入れ条件（`docs/design/implementation-plan.md`）と要件（`docs/product/PRD.md`）からテスト計画を作り、`docs/test/` に置く。
2. 自動テスト（pytest。保存したログを時刻順に流す再生テストを含む）を `tests/` に足し、仕組みの検査で動くようにする（`tests/` に触れる PR は、マージの前の検査で E2E が動く。全部を通すのは、手で動かす `CI` の `full`。D-P21）。マイクは偽の入力（既知の周波数の音声ファイル）で試す。
3. 見つけた不具合は、再現手順・期待・実際・環境を書いた Issue にする。実装の誤りなら `role:impl` を付けて 起動用の PR（番号は STATUS.md に書く） に `WAKE` を書く。設計や要件の問題なら `role:pm`。
4. 実機でしか確かめられない項目は、`needs-human` の Issue に手順（番号つき、10 分以内）を書く（README の 8 章の書式。`返事の行き先:` は、結果を受けて直す `role:impl`）。
5. テストの PR には `role:impl-review` を付ける。

## 自分の PR に指摘・検査の失敗・競合が戻ってきたとき

変更したファイル（改名なら元の場所も）の全部が `docs/test/` か `tests/` の下にある PR は、テスターが直す。

1. 最新のレビュー・検査失敗・競合のコメントを読み、`着手: テスター <日時（JST）>` をコメントする。
2. 指摘と失敗を直し、競合や main の更新を取り込んで、同じブランチにコミットしてプッシュする（強制プッシュはしない）。[必須] はすべて直し、[推奨] は対応するか見送る理由を書く。手元で `bash .github/scripts/verify.sh . e2e`（動かせない環境なら個別のコマンド）を実行し、結果を PR に記録する。
3. アプリ本体（`src/`）を直さないと通らない指摘は、自分では直さない。再現手順・期待・実際・環境を Issue にし、実装の誤りは `role:impl`、設計や要件の問題は `role:pm` へ渡す（上の3項）。元の PR に依存先と未解決の点を残す。
4. 自分の範囲の修正が済んだら、指摘ごとの対応と検査結果をコメントし、自分の `role:test` を外して `role:impl-review` を付ける。そのあと、起動用の PR（番号は STATUS.md に書く） に `WAKE role:impl-review #<PR番号>` を書く。承認・マージを自分で行わない。
