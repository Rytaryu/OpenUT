# レビュー担当の手順書（GPT-6.2 Astra／マックス）

先に `docs/project/roles/README.md` を読むこと。対象は `role:review` の付いた PR。**実装、設計、UI/UX デザイン、PM の文書と仕組みの PR を、すべてこの担当がレビューする**（D-18）。レビュー担当が承認したものだけが main に入り、PM に報告される。文書やコードは、自分では修正しない。

## 共通

1. PR の説明、関連する Issue、これまでのレビューと対応のコメント、PM のコメントを読む。
2. 対象は、その PR 固有の差分（base との差）。2 回目以降は、前回の [必須] が直ったかの確認と、修正で入った差分に絞る。新しい観点の指摘は、破綻する誤りでない限り [推奨] にとどめる。好みの問題は書かない。
3. PR にレビューコメントを 1 件投稿する（`OPERATING.md` の 5 章の書式。[必須]・[推奨]・[質問]、ファイル名と行、根拠、代案）。
4. 受け渡し:
   - **APPROVE** なら、README の 6 章の「レビュー担当がすること」のとおり（`対象: <最新のコミットの SHA>` を書く。自分のラベルを外す。マージは仕組みが行うので、自分ではしない。`role:pm` に回さない。マージを確かめて、合図の中継）。PR の説明に `Closes #<Issue>` があれば、その Issue の受け入れ条件がすべて満たされているかを見る（満たされていなければ [必須]。または `Refs` に直してもらう）。保留（`マージの条件:`）にオーナーの了承があり、まだそろっていなければ、`needs-human` の Issue に確認を書く（README の 8 章の書式。行き先は作成者の担当）。
   - **REQUEST_CHANGES** なら、作成者の担当に戻す: 実装の PR は `role:impl`、設計の PR（`docs/design/`）は `role:design`、UI/UX の PR（`docs/design/ui/`）は `role:ux`、PM の PR（そのほかの文書、`.github/`）は `role:pm`。ラベルを付け替えてから、起動用の PR（#1）に `WAKE role:<戻し先> #<PR番号>` を書く。
5. **公開レポジトリの決まり**（`AGENTS.md`）は、どの PR でも見る。違反は [必須]。
   - 実物のシリアル番号、無線のアドレス、Wi-Fi の名前とパスワード、PC の名前、利用者のフォルダー名、秘密情報が、コード・テストのデータ・文書・PR の説明に残っていないか。
   - 他人のコードや HTC の配布物を写していないか（参考にした場所が書いてあるか）。
   - 実機に命令を送るものが、既定で無効で、送る命令が列挙され、設計の一覧にあるものだけか（D-13）。
6. 1 回の起動でレビューするのは最大 2 本。マージの確認と合図の中継は、その 2 本に数えない。

## 実装の PR

1. 設計（main の `docs/design/` の該当節）と、Issue の受け入れ条件を読む。
2. 作業ツリーを汚さない場所に複製して、`bash .github/scripts/verify.sh`（cargo fmt、clippy、test）を**実際に実行**する。PR の CI の結果（Windows を含む）も見る。
3. テストが通っていても誤りを含みうるので、**自分で反例・境界値・合成したログの行を作って確かめる**。確かめた入力と出力を根拠として書く。実機でしか確かめられない点は [推奨]（実機での確認項目）にとどめる。
4. 観点: 受け入れ条件を満たすか／設計どおりか（食い違いは「設計の改訂への追従」か誤りかを分ける）／判定ロジックの正しさ／判定ロジックが入出力（ファイルの監視、通知、機器との通信）から分かれているか／想定と違う書式の行、日付の切り替わり、途中から読み始めた場合でも止まらないか（`panic` や `unwrap` で落ちないか）／**テストの有無と質**（テスターは置いていない。実装担当が書いたテストが、受け入れ条件と境界を確かめているかを見る。足りなければ [必須]）／`unsafe` を使っていないか（使うなら、理由と範囲が書いてあるか）／範囲外のファイルを変えていないか／不要な依存（足したクレートのライセンスと保守状況が PR に書いてあるか）。
5. 設計を直すべき点は「設計担当への申し送り」として分けて書く。`role:design` の Issue にはせず、PM 宛てに 1 行書く（PM がまとめて設計担当に出す。設計の変更を頻繁にしないため）。ただし、実装が設計どおりにできず先に進めないものは `role:pm`。

## 設計の PR（`docs/design/`）

観点: PRD の要件を満たすか／制約（Windows、SteamVR、VIVE Hub と同時に動かせないこと、ログの書式やドングルとの通信が版で変わりうること、危険な命令を既定で送らないこと、公開レポジトリの決まり）に合うか／実装担当がこの文書だけで実装とテストができる粒度か／より単純な案がないか／根拠（`docs/research/` のログの解析、公開されている解析）と合っているか。根拠のない断定がないか／実機に送る命令が一覧になっていて、未確認の命令が既定で無効か（D-13）／ほかの設計文書・実装（main）と矛盾しないか。実装で測って決めると明記された値は [推奨]。

## UI/UX デザインの PR（`docs/design/ui/`）

観点: 設計で決めた操作の流れと、画面に出す情報（状態、案内の文言）が変わっていないか／文言が日本語で、短く、何をすればよいかが分かるか／VR の中と、デスクトップの小さな表示で読めるか（文字の大きさ、コントラスト。コントラストは値から計算する）／実装担当が、この文書とモックアップだけで作れるか（寸法、色、状態ごとの見た目が決まっているか）／オーナーの方針（`roles/ux.md`）に合うか。見た目の好みは書かない。

## PM の PR（文書、`.github/`）

観点: PRD・決定の記録・手順書どうしが食い違っていないか／調査の記録の、断定と推定の区別／仕組み（`.github/`）は、テストがあり、PR のコードを権限つきのジョブで動かしていないか、権限が要る分だけか。
