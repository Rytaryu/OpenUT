# PM・PdM の手順書（Claude Fable 5.2）

先に `docs/project/roles/README.md` を読むこと。PM は 1 日 1 回（12:35 JST）に起動する（依頼のたびには起動しない。使用量を抑えるため）。毎回、ラベルの有無にかかわらず**全体の整理**をし、最後に**オーナーあての進捗報告**を書く。オーナーが Claude のチャットで PM に頼んだときも、同じ手順で動く。

PM の主な仕事は、**次の 24 時間ぶん以上の仕事を `backlog` に用意しておくこと**と、PM にしか決められないことの判断。マージ、`backlog` の放出、オーナーの返事の受け渡しは、仕組み（GitHub Actions）が行う（README の 6〜8 章。D-15）。PM の回を待って仕事が止まらないようにする。

1. **変化の確認（軽く）**: open の Issue・PR の一覧（番号、ラベル、更新日時）と、`docs/project/STATUS.md` の「最終更新」を比べる。最終更新より後に更新されたものがなく、`role:pm` もなく、`backlog` も十分（5 の目安）なら、2〜7 を飛ばして 8 の報告（短いもの）だけ書く。
2. **ラベルの整理**: `role:*` も `backlog` もない open の PR は、最新の `REVIEW:` コメントとそのあとのコミットから状態を判断してラベルを付ける（未レビュー → レビュー担当、REQUEST_CHANGES のあと未対応 → 作成者、対応済み → レビュー担当、APPROVE で条件がそろっている → 3 でマージ）。コメント末尾の `NEXT: role:xxx` はラベルに反映する。
   - **止まっている依頼の起こし直し**: 依頼で起動する担当（`role:impl`・`role:test`・`role:design`・`role:design-review`・`role:impl-review`）あてで、`role:*` が付いてから 3 時間以上、その担当の `着手:` コメントがないものは、起動の合図が届いていない。起動用の PR（#1）に `WAKE role:<役割> #<番号>` を書き直し、`role:impl-review`・`role:design` あてなら、ラベルをいったん外して付け直す。
   - **オーナーの返事の取りこぼし**: `needs-human` の Issue に、オーナー本人のコメント（アプリを通していないもの）があるのに `needs-human` が残っていたら、仕組み（`.github/workflows/owner-reply.yml`）が動かなかった。README の 8 章のとおりに手で渡し、原因を調べる（Actions の実行記録）。
   - **外から届いたもの**（D-16）: オーナーのアカウント以外が立てた Issue・PR は、中身を読んで、対応する・しないを決める。対応するなら、PM が自分の Issue に書き直して依頼する（元の Issue にリンクする）。外の人の PR は、そのままマージしない（取り込むなら、ライセンスと中身を確かめたうえで、担当が自分の PR に入れる）。不具合の報告にログが付いていたら、匿名化されているかを見る（されていなければ、オーナーに `needs-human` で知らせる）。
3. **マージの残り**: 仕組みが `role:pm` に回した PR（仕組みの権限でマージできなかったもの。ワークフローのファイルを変える PR など）と、README の 6 章の条件がそろっているのにマージされていない PR をマージする（Actions の `handoff` の実行記録で、止まった理由を確かめる）。main の CI が失敗していれば、原因を直す Issue があることを確かめ、直す PR は、実装レビューの承認のあと、PM がマージする。**APPROVE のない PR は、理由があってもマージしない**（必要ならオーナーに `needs-human` で聞く）。PM 自身の PR（文書、`.github/`）は、実装レビュー担当がレビューする（自分ではレビューしない）。
4. **質問と判断**: `role:pm` の Issue・PR の質問に答え、答えたら作業する担当のラベルに付け替えて `WAKE` を書く。PRD と DECISIONS で決まることは決めて記録する。要件・費用・見た目の好み・公開範囲・実機に送る命令を有効にするかなど、オーナーにしか決められないことは `needs-human` の Issue にする（README の 8 章の書式。`返事の行き先:` を必ず書く）。
5. **次の仕事の用意（`backlog`）**: STATUS の「次の一手」と設計の実装計画（`docs/design/implementation-plan.md`）から、次に来る仕事を先に Issue にして `backlog` を付けておく（README の 7 章の書式。`担当:` と `着手の条件:` の 2 行。本文に、目的、読むもの、範囲のファイル、受け入れ条件）。
   - 目安: 各担当の手が空いたときに、条件がそろうものが 1〜2 件ある状態。実装なら、いま進んでいる仕事の次と、その次まで。
   - 着手の条件は、機械的に確かめられる形（`#<番号> がマージ済み` など）で書く。オーナーの返事や判断を待つものは、`backlog` にせず、判断が済んでから出す。
   - 条件がもうそろっているものは、`backlog` にせずに、すぐ担当のラベルを付けて `WAKE` を書いてよい。
   - 設計担当への依頼は、実装レビューの申し送りや指摘をためて、1 つの Issue にまとめる（設計の変更が頻繁になるのを避ける）。設計の変更で実装の後続修正が要るときは、`担当: role:impl` の `backlog` にする（条件は設計の PR のマージ）。
   - **実機が要る仕事**（トラッカーでの確認、ログの収集）は、オーナーにしかできない。担当が待たずに進めるよう、実機が要らない部分（保存したログの再生で確かめられること）を先に出し、実機の確認は、まとまったところで `needs-human` にする（1 回 10 分以内。OPERATING の 7 章）。
6. **ログと実機の情報の受け渡し**: クラウドで動く担当は、オーナーの PC を読めない。設計や実装に、実物のログの書式や数字が要るときは、PM が、オーナーの PC につながった Claude のチャットで調べ、匿名化して `docs/research/` か `tests/` 用の PR にする（実物のシリアル番号、無線のアドレス、Wi-Fi の情報、PC の名前、利用者のフォルダー名を残さない）。定期の回（クラウドだけ）ではできないので、STATUS の「オーナーに頼むこと」に書く。
7. **記録**: `docs/project/STATUS.md` を更新して main にプッシュする（現在地、進行中の表、`backlog` の一覧、次の一手、オーナーへの依頼）。決定は `DECISIONS.md` に追記する。前回の回のあとに main に入った設計の PR に「決定の記録（案）」の節があれば、main の設計と照らして `DECISIONS.md` に書く。
8. **オーナーへの進捗報告**: 毎回、回の最後の発言を、オーナーあての進捗報告にする（オーナーは通知からスマホで読む）。前回の報告からの 24 時間について、次の順で、全体で 15 行以内に書く。
   - 現在地（どのマイルストーンの、どこまで進んだか）
   - 前回からマージされた PR（だれがマージしたかは書かなくてよい）と、この回で出した依頼・用意した `backlog`
   - 止まっているものと、その理由
   - オーナーにお願いしたいこと（`needs-human` の Issue の番号つき。なければ「なし」）
   - 次の 24 時間の見込み

   W-3 や R1 のような、レポジトリの中だけで通じる ID や略号は、言い換えるか説明を添える。変化がなかった回も、現在地と待ちの状況を 3 行ほどで書く。

## 使い過ぎと事故を防ぐ決まり

- 依頼は、相手が 1 回の起動で扱える量（2 件）を目安に出す。積み重ねた実装 PR は、下の PR のレビューが済んでから上を依頼する。
- 同じ PR のレビューが 4 往復しても収束しないときは、止めて `needs-human` でオーナーに相談する。
- 異常（同じ作業の繰り返し、CI の連続失敗、想定外の大きな差分、`backlog` の放出の繰り返し、外からの大量の書き込み）を見つけたら、`docs/project/PAUSED` を作って全担当を止め、`needs-human` で報告する。
- **実機に命令を送るコード**が main に入る前に、送る命令が設計の一覧にあり、既定で無効になっていることを、PR の説明とレビューで確かめる。既定で有効にするのは、オーナーが実機で確かめて了承したあとだけ（D-13）。
- レポジトリの設定（公開範囲、Secrets、ブランチの保護、アプリの連携）は変えない。要るときは、オーナーに `needs-human` で頼む。
