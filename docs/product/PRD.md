# 要件（PRD）

PM が所有する。変えたいときは Issue か PR で PM に戻す。

## 解く問題

VIVE Ultimate Tracker 3 台と VIVE Wireless Dongle を、Meta Quest 3 と SteamVR（Windows）で使っている。VIVE Hub 2.5.6（Ultimate Tracker ランタイム 1.2.5）で、次の 2 つが起きる。

1. **始まらない。** 一部のトラッカーが、位置を出せないまま止まる。全台の電源を切ってドングルをリセットしても、同じことが繰り返される。
2. **途切れる。** 使っている途中で追跡を失い、長いときは数分戻らない。

1 は PC 側のソフトの不具合と確かめられた。2 はトラッカーの中で起きていて、理由は未確認。根拠は `docs/research/findings-2026-11-27.md`。

## 使う人

オーナー本人。公開するので、同じ構成の人が使えるように、設定を自分の環境に固定しない。

## 段階1: 見張り役

VIVE Hub を使ったまま、横で動かす。

| 番号 | 要件 |
|---|---|
| W-1 | VIVE Hub のトラッカー用サーバーのログ（`ViveTrackerServer_YYYYMMDD.txt`、UTF-16、0 時に切り替わる）を、追記された分だけ読み続ける。 |
| W-2 | トラッカーごとの状態（未接続、接続、Wi-Fi 待ち、地図同期中、位置取り直し中、追跡中）と、PC がホストの Wi-Fi 情報を持っているかを保つ。 |
| W-3 | 「Wi-Fi 情報なし」の不具合を検出し、どのトラッカーの電源を入れ直せばよいかを案内する。全台の電源オフやドングルのリセットは勧めない。 |
| W-4 | 地図同期が遅い、ホストが位置を出せない、操作と関係のない切断、を検出して案内する。 |
| W-5 | 案内を SteamVR の中とデスクトップの両方に出す。同じ案内を繰り返し出しすぎない。 |
| W-6 | 日ごとの集計（位置が出ていた割合、喪失の回数、不具合の回数）をファイルに残す。 |
| W-7 | 実機に命令を送らない。ログを読むだけ。 |
| W-8 | 保存したログを時刻順に流す再生テストで、検出の規則を確かめられる。 |

### 受け入れの基準

- 2026-11-22〜27 のログを流すと、W-3 の検出が 4 回だけ出る（11/26 01:43、11/27 22:53・22:56・22:59）。
- VIVE Hub と SteamVR を動かした状態で、VR の動作を重くしない。
- ログの書式が想定と違う行に出会っても、止まらずに読み続ける。

## 段階2: 置き換えランタイム（概要）

VIVE Hub のトラッカー用サーバーの代わりに、ドングルを直接扱う。段階1 の記録を見てから、要件を書く。いま分かっている骨組みは `docs/design/overview.md`。

- ホストの選択、Wi-Fi 情報の保持と配布、地図同期の監視
- 喪失中は最後の正しい位置を保ち、回転だけ更新する。大きな飛びを SteamVR に渡さない
- SteamVR へのトラッカーの登録（役割はシリアル番号で固定）
- HMD の空間との位置合わせを、自前のファイルに保存する

## やらないこと

- トラッカーのファームウェアの書き換え、SLAM の差し替え（D-3）
- 地図の作成、ファームウェアの更新、ペアリング（D-7）
- 実機への自動の復旧操作（D-6）
