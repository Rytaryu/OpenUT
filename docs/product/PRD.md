# 要件（PRD）

PM が所有する。変えたいときは Issue か PR で PM に戻す。最終更新: 2026-11-28（OpenUT の位置付けの決定 D-9〜D-14 と、Rust で作る決定 D-17 を反映）。

## 1. 解く問題

VIVE Ultimate Tracker 3 台と VIVE Wireless Dongle を、Meta Quest 3 と SteamVR（Windows）で使っている。VIVE Hub 2.5.6（Ultimate Tracker ランタイム 1.2.5、ファームウェア 1.0.999.178）で、次のことが起きる。根拠は `docs/research/` の調査の記録。

| 問題 | 起きている場所 | 分かっていること |
|---|---|---|
| **始まらない。** 一部のトラッカーが、位置を出せないまま止まる。全台の電源を切ってドングルをリセットしても繰り返す | PC 側（VIVE Hub のトラッカー用サーバー） | サーバーが、ホストの Wi-Fi 情報を持たない状態になり、後から来たトラッカーに渡せない。6 日で 4 回 |
| **走り出してから失う。** 「追跡中」と報告したまま推定位置が一方向へ走り出し、そのあと追跡を失う | トラッカーの中（SLAM） | 1 晩で 2 回。数秒で 2〜6 m ずれた。同じ時刻、ほかの 2 台は動いていない |
| **クラッシュ。** トラッカーの中のソフトが落ちて、接続ごと切れる | トラッカーの中（SLAM） | 3 台で 4 か月に 12 件。月に 2〜3 回 |
| **起動直後に位置が出ない。** 位置合わせに 20〜60 秒、長いと数分かかる | トラッカーの中（SLAM） | 静止したまま起動すると、数分のあいだ失敗し続けた回がある |
| **長い喪失。** 使っている途中で、数分戻らない | トラッカーの中 | 理由は未確認。起きた日のトラッカー内のログがまだない |

ファームウェアは自作しない（D-10）。トラッカーの中で起きる問題は、PC 側で早く見つけて、位置を止める・立て直す・知らせることで、使い心地を良くする。

## 2. 作るもの

**OpenUT は、VIVE Hub の代わりに、VIVE Ultimate Tracker を SteamVR で使うための PC 側のソフトウェア**（D-9）。

- 日々の利用（追跡の開始、SteamVR への受け渡し）、ペアリング、部屋の地図の作成を、すべて受け持つ。
- VIVE Hub の「始まらない」不具合を起こさない。
- トラッカーの中の SLAM のクラッシュと暴走を、素早く検知して立て直す。
- 目標は、**OpenUT を入れて起動すれば使える**こと。日々の利用で VIVE Hub を必要としない（D-11）。
- ファームウェアとドライバーの更新だけは、VIVE Hub のものをそのまま使う（D-11）。
- 不調のときのログを集めて、匿名化して送れる（D-12）。
- Windows のアプリとして、Rust で作る（D-17）。

## 3. 使う人

- オーナー本人（トラッカー 3 台、ドングル 1 台、Meta Quest 3）。
- 公開するので、同じ機器を使うほかの人。オーナーは、ほかの人にも試してもらい、不調のときのログを送ってもらうつもりでいる（D-12）。設定を、オーナーの環境（台数、シリアル番号、フォルダー、HMD）に固定しない。

## 4. 作る順番

| 段階 | 作るもの | VIVE Hub | 実機 | 終わりの目安 |
|---|---|---|---|---|
| M0 土台 | 検査、受け渡しの仕組み、ログの匿名化の道具、再生テスト用のログ | — | 不要 | 匿名化したログが `tests/` にあり、再生テストの枠組みが CI で動く |
| M1 見張り役 | VIVE Hub のログを読み、始まらない・途切れる理由と対処を、その場で知らせる。ログの収集 | そのまま使う | 読むだけ | 5 章の受け入れの基準 |
| M2 ドングルの読み取り | VIVE Hub を止めた状態で、ドングルから状態と姿勢を読むだけの道具 | 止める | 読むだけ（命令を送らない） | 3 台の状態と姿勢が読め、VIVE Hub のログの値と合う |
| M3 日々の利用 | ペアリング済み・地図作成済みのトラッカーで、追跡を始めて SteamVR に渡す。検知と立て直し | 使わない（ペアリングと地図は VIVE Hub で済ませておく） | 命令を送る | VIVE Hub なしでフルトラッキングができ、「始まらない」が起きない |
| M4 ペアリング | トラッカーとドングルのペアリング | 使わない | 命令を送る | 新しいトラッカーを OpenUT だけで使い始められる（地図を除く） |
| M5 地図の作成 | 部屋の地図を作る・作り直す | 使わない | 命令を送る | VIVE Hub を入れていない PC で、最初から使える（ファームウェアの更新を除く） |

- M1 と M2 は並べて進める。M1 は VIVE Hub を使ったままなので、M3 ができるまでの毎日の助けになり、M1 で作る「状態」「検出の規則」「通知」「再生テスト」は M3 でそのまま使う。
- ログの送信（6 章の L-4・L-5）は、送り方が決まってから、M1 のあとに入れる。
- M3 より先の要件（7〜9 章）は概要。M2 の結果を見て、PM が書き足す。

## 5. M1: 見張り役

VIVE Hub を使ったまま、横で動かす。

| 番号 | 要件 |
|---|---|
| W-1 | VIVE Hub のトラッカー用サーバーのログ（`ViveTrackerServer_YYYYMMDD.txt`、UTF-16、0 時に切り替わる）を、追記された分だけ読み続ける。 |
| W-2 | トラッカーごとの状態（未接続、接続、Wi-Fi 待ち、地図同期中、位置取り直し中、追跡中）と、PC がホストの Wi-Fi 情報を持っているかを保つ。 |
| W-3 | 「Wi-Fi 情報なし」の不具合を検出し、どのトラッカーの電源を入れ直せばよいかを案内する。全台の電源オフやドングルのリセットは勧めない。 |
| W-4 | 地図同期が遅い、ホストが位置を出せない、操作と関係のない切断、を検出して案内する。 |
| W-5 | 案内を SteamVR の中とデスクトップの両方に出す。同じ案内を繰り返し出しすぎない。 |
| W-6 | 日ごとの集計（位置が出ていた割合、喪失の回数、不具合の回数）をファイルに残す。 |
| W-7 | 実機に命令を送らない。ログを読むだけ（D-13）。 |
| W-8 | 保存したログを時刻順に流す再生テストで、検出の規則を確かめられる。 |
| W-9 | ログの置き場所、トラッカーの台数、シリアル番号を、オーナーの環境に固定しない（設定か、自動で見つける）。 |

### 受け入れの基準

- 2026-11-22〜27 のログ（匿名化したもの）を流すと、W-3 の検出が 4 回だけ出る（11/26 01:43、11/27 22:53・22:56・22:59）。
- VIVE Hub と SteamVR を動かした状態で、VR の動作を重くしない。
- ログの書式が想定と違う行に出会っても、止まらずに読み続ける。

## 6. ログの収集と送信（D-12）

| 番号 | 要件 | 段階 |
|---|---|---|
| L-1 | 匿名化の道具。ログの中の、シリアル番号、無線のアドレス、トラッカー同士の Wi-Fi の名前とパスワード、PC の名前、利用者のフォルダー名を置き換える。同じ値は同じ置き換えになり、ファイルをまたいで突き合わせができる。置き換えた結果に、元の値が残っていないことを確かめる手段を持つ。 | M0 |
| L-2 | 再生テスト用のログは、L-1 の道具で作る。 | M0 |
| L-3 | トラッカー内のログの束を、USB でつないだ全トラッカーから、1 回の操作で取り出し、日時とトラッカーごとに並べて保存する。使ったあと毎回取って、いろいろな場合をためられるようにする。 | M1 |
| L-4 | 送る前に匿名化し、**利用者が中身を確かめてから送る**。自動では送らない。トラッカー内のログには体の動き（位置と向き）の記録が入ることを、送る前に利用者に示す。 | M1 のあと |
| L-5 | 送り方は未定。アプリから送ると、レポジトリに Issue が（なければ）立つ形が理想。設計の前に、オーナーと決める。 | M1 のあと |

- つなぎとして、オーナーの PC に収集用のスクリプトがある（HTC の取り出しツールを呼ぶもの。実機ではまだ確かめていない）。L-3 は、これを確かめたうえで作る。
- トラッカー内のログの取り出しは、いまは VIVE Hub に同梱のツールに頼っている。D-11 の目標（VIVE Hub を必要としない）に合わせて、自前で取り出せるかは、設計で調べる。

## 7. M2: ドングルの読み取り（概要）

| 番号 | 要件 |
|---|---|
| DG-1 | Windows で、ドングルにつながったトラッカーの状態（接続、役割、地図の状態、追跡の状態）と姿勢を読む。 |
| DG-2 | **命令を送らない。** 読むために送らなければならないもの（問い合わせ）があるなら、設計で一覧にし、オーナーの了承を得る（D-13）。 |
| DG-3 | VIVE Hub のサーバーが動いていたら、起動を断って理由を示す（ドングルは同時に 1 つのプログラムしか扱えない前提。前提が正しいかも確かめる）。 |
| DG-4 | 読んだ値を、時刻つきで記録できる（M3 の再生テストの入力になる）。 |

## 8. M3: 日々の利用（概要）

| 番号 | 要件 |
|---|---|
| R-1 | ドングルを直接扱い、VIVE Hub のサーバーなしで、ペアリング済みのトラッカーの追跡を始められる。 |
| R-2 | ホストの選択、Wi-Fi 情報の保持と配布、地図同期の監視。Wi-Fi 情報は、ホストが替わるまで消さない。尋ねられて持っていなければ、ホストに問い合わせる（「始まらない」を起こさない）。 |
| R-3 | SteamVR にトラッカーとして登録する。役割（腰、足）は、トラッカーごとに固定する。 |
| R-4 | HMD の空間との位置合わせを、自前のファイルに保存する。 |
| R-5 | 喪失中は、最後の正しい位置を保ち、回転だけ更新する。大きな飛びを SteamVR に渡さない。 |
| R-6 | **暴走の検知。** 「追跡中」のまま推定位置が走り出したこと（向きがほぼ変わらないのに速さが増え続け、ほかのトラッカーが動いていない）を検知して、位置を止める。目安は、1 m ずれる前。 |
| R-7 | **クラッシュと長い喪失の検知と立て直し。** トラッカーの中のソフトが落ちたこと、追跡が戻らないことを検知して、立て直し、利用者に知らせる。立て直しで送る命令は、設計で一覧にし、実機で確かめてから既定で有効にする（D-13）。 |
| R-8 | 起動直後の位置合わせを待っているあいだ、何をすればよいか（トラッカーを部屋へ向けて動かす）を知らせる。 |
| R-9 | 状態の表示と案内は、M1 の見張り役を使う（入力を、ログから、ランタイムの出来事に差し替える）。 |
| R-10 | インストールして起動すれば使える。VIVE Hub が入っていることを前提にしない（D-11）。 |

## 9. M4・M5（概要）

- **M4 ペアリング**: トラッカーとドングルのペアリングを OpenUT で行う。
- **M5 地図の作成**: 部屋の地図の作成と作り直しを OpenUT で行う。地図はトラッカーの中にあり、3 台で共有される。
- どちらも、ドングルやトラッカーへの書き込みにあたる命令を使う見込みが高い。M2・M3 で通信が分かってから、要件を書く。

## 10. やらないこと

- トラッカーのファームウェアの書き換え、SLAM の差し替え（D-10）。
- ファームウェアとドライバーの更新の機能（VIVE Hub のものを使う。D-11）。
- HTC のバイナリ、ファームウェア、HTC の更新サーバーへの問い合わせに使う値を、配布物やレポジトリに入れること。
- ログの自動送信（L-4）。
- 見張り役（M1）からの、実機への自動の復旧操作（D-13）。

## 11. 守ること（全段階）

- **危険な命令を既定で送らない。** ドングルやトラッカーを再起動させる命令と、書き込みの命令は、一覧にして既定で禁止する。実機に命令を送る機能は、設計の一覧にあり、オーナーが実機で確かめたものだけを有効にする（D-13）。
- **個人の情報を外に出さない。** レポジトリ、Issue、送るログに、実物のシリアル番号、無線のアドレス、Wi-Fi の情報、PC の名前、利用者のフォルダー名を入れない。
- **他人のコードを写さない。** 先行する解析（`docs/research/findings-2026-11-27.md` の「先行事例」）は参考にするが、ライセンスの表示がないものは写さない。
- UI の文言は日本語。
