# 調査の記録（2026-11-29）: 11/28 の夜の喪失と、ログの台の対応

オーナーが 2026-11-28 23:14〜11-29 01:51 にフルトラッキングを使い、「2 台が途切れたり飛んだりした」と報告した夜のログを読んだ結果。シリアル番号などの個人の情報は載せていない。台は VIVE Hub のログの `device index` と役割で呼ぶ。

**読み方。** 「ログにあったこと」は記録の値をそのまま数えたもの。「推定」はその値から PM が読み取ったことで、実機では確かめていない。元のログはレポジトリに入れていない（オーナーの PC にある）。

## 結論

- **この夜の長い喪失は、無線ではなくトラッカーの中の位置の推定（SLAM）が外れたもの。** 喪失のあいだもドングルとの無線の取りこぼしは増えていない。PC 側のソフト（VIVE Hub でも OpenUT でも）が無線の扱いを変えて直せる種類の喪失ではない。
- 長く外れたのは 1 台（クライアント、`device index` 0）で、01:28〜01:40 に 3 回、合わせて 9 分あまり。ホストは同じ時間帯に 15 秒以下が数回。残りの 1 台は 1 秒未満が 3 回。
- **台の対応が取れた。** VIVE Hub のサーバーのログの `device index`、ドライバーとドングルのログのスロットの番号、トラッカーの中のログの `device_id` は同じ番号。
- ドライバーが起動のときに送る `power state` の 21 と 11 は、トラッカーの中のログの `tracking_mode` の 21（ホスト）と 11（クライアント）に対応する。K4 の設計（#57）の材料。
- OpenUT で対処できること（推定）: 喪失を早く知らせる、喪失のあいだの姿勢を SteamVR に「正しくない」と渡す（設計の表のとおり）。喪失そのものを減らすのは、使う場所（明るさ、カメラの視界）の側。

## 読んだもの

- VIVE Hub のログ（PC 側）: サーバー、ドライバー、ドングルの 11/28 と 11/29 のファイル。
- トラッカーの中のログの束（3 台。フルトラッキングのあと、電源を入れ直す前に取り出したもの）の `sys_log/current/log.txt*`。`tracking_log/`（SLAM の細かい記録）は、今回は読んでいない。
- 確かめた範囲: オーナーの PC 1 台、トラッカー 3 台、1 晩。版はサーバーのログに出ていたトラッカーのファームウェア 1.0.999.178。

## 台の対応（ログにあったこと）

| VIVE Hub のサーバー（`device index`） | ドライバー・ドングル（スロット） | トラッカーの中（`horusd_dump_stats` の `device_id`） | 役割 | `tracking_mode` |
|---|---|---|---|---|
| 1 | 1 | 1 | ホスト | 21 |
| 0 | 0 | 0 | クライアント | 11 |
| 3 | 3 | 3 | クライアント | 11 |

- 根拠 1: ホストの台の束だけに、ホストの側の受け渡しの行（`ft_host_accept` など）がある。サーバーのログで `is host: 1` なのは `device index` 1。
- 根拠 2: 下の喪失の時刻が、サーバーのログとトラッカーの中のログで、台ごとに 1 秒以内で一致する。
- ドライバーのログでは起動のときに `(1) StartTracker, power state: 21`、`(0) StartTracker, power state: 11`、`(3) StartTracker, power state: 11`。
- サーバーのログの `sn` は adb で見えるシリアル番号とは別の番号だった。束のファイル名（adb のシリアル番号の末尾）からサーバーのログの台を引くには、上の `device_id` を使う。
- サーバーの `display index`（VIVE Hub の画面の並び順）は、0 がホスト、1 が `device index` 0、2 が `device index` 3 だった。

## 喪失のあいだに起きていたこと（ログにあったこと）

**無線（ドングルのログの `dumpPUMRFDropRate`）。** 台ごと、約 8 秒ごとの報告を足したもの。

| 時間帯 | スロット 0 | スロット 1 | スロット 3 |
|---|---|---|---|
| 23:17〜01:20 | 2.8 / 1000 | 2.0 / 1000 | 2.9 / 1000 |
| 01:20〜01:28 | 3.4 / 1000 | 1.8 / 1000 | 7.7 / 1000 |
| **01:28〜01:40（長い喪失）** | **3.6 / 1000** | 1.9 / 1000 | 3.7 / 1000 |
| 01:40〜01:52 | 0.1 / 1000 | 0.7 / 1000 | 0.4 / 1000 |

- 続けて失った数（`MAX RF-LOST`）は、どの時間帯も 1〜2。
- 長い喪失のあいだもスロット 0 の取りこぼしは 0.4% ほどで、ふだんと変わらない。

**トラッカーの中（クライアント 0 の `sys_log`）。**

- 01:28〜01:40 に、`SLAM : [RelocByFeature] …, inliers: N`（地図の中の自分の位置を探し直す記録）が 194 行。01:00〜01:12 には 0 行。
- この行の `inliers` は 01:20 台と 01:30 台で中央値 52（最小 50）。起動の直後（23:14〜）は中央値 148。
- 戻る直前に `SLAM : [doLiveK] Force LiveK init.`（01:29:27、01:39:51、01:40:00）。
- カメラのフレームレートの行、IMU の行、温度の行の数は喪失のあいだと前で変わらない。
- 外れてから 10 秒後に、`[ack] … send ack=P82:0:0`（Wi-Fi でホストへ）。戻ったときに `P82:0:8`。

## 推定（確かめていない）

- **喪失の原因は、カメラの画像から地図の中の位置を決められなくなったこと。** 根拠は、無線が正常なまま `RelocByFeature` が続いたことと、`inliers` が起動のときの 3 分の 1 ほどで、最小の 50 に近い値が並んでいること。カメラが体や物で隠れた、部屋が暗くなった、地図にない向きを見ていた、のどれかはログからは分からない（その時刻にオーナーがどうしていたかを聞く）。
- **`OET LOST TRACKING! index: 1` は、クライアントが「10 秒たっても戻らない」とホストに伝え、ホスト（`device index` 1）経由でサーバーに届いた知らせ。** 根拠は、クライアントの `send ack=P82:0:0` の 1 秒後に出ていることと、3 回とも外れたのはクライアント（0）で、ホストは追跡中だったこと。`index: 1` が「知らせを運んだ台」なのか別の意味なのかは、確かめていない。ログ監視（M1）がこの行を「`index` の台が外れた」と読むと、台を取り違える。
- `tracking result` の 200 は追跡中、301 は喪失（位置を探し直している）。201 は起動の直後にだけ出た（意味は確かめていない）。

## 確かめていないこと

- 01:40 以降に、3 台とも無線の取りこぼしが 0 に近づいた理由。
- `tracking_log/`（SLAM の細かい記録、毎フレームの記録）。喪失の前後で、カメラごとの特徴点の数や明るさがどう変わったかは、ここにあるはず。
- ホストの束に、01:40 台の `RelocByFeature` が 211 行ある（`inliers` の中央値 135）。ホストの喪失は 15 秒なのに行が多い理由。
- 「飛んで行った」（位置が大きくずれた）場面が、どの時刻のどの台か。喪失（`tracking status` 4）の記録だけでは、位置が飛んだかどうかは分からない。
- VIVE Hub のサーバーの `tracking status` の 4 と、ドングルの報告の追跡の状態（設計の表の 2・3・4）が同じ番号かどうか。
