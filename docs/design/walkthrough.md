# 通し版の設計（全体を粗く通す最初の版）

VIVE Hub を起動せずに、ペアリング、地図の作成、追跡の開始、SteamVR への受け渡し、スペースキャリブレーション、状態の表示を、一通りできるようにする最初の版（通し版）の設計。Issue #57、D-41（2026-11-28 のオーナーの指示: 機能を 1 つずつ仕上げず、全体を粗く通してから、使いながら直す）。

**この文書は第 1 版（骨組み）。** Issue #57 の 1〜7 のうち、1（全体の形）、5（実機で確かめる順序）、7（実装計画の最初の切れ目）を先に書いた。2（VIVE Hub の順序）、3（送る命令）、4（キャリブレーション）、6（いまあるものの使い方）は、いま分かる範囲と、最初の 3 つの切れ目に要る分を書いた。残りは次の PR で足す（10 章）。第 1 版へのレビュー（PR #60）と PM の決定（D-43、D-45）を受けて、1.3.4（台を足す順序）、3.1（確かめる前の命令の送り方）、4.3.4（軸の並べ替えの選び方と、トラッカー自身の向き）を直した。

根拠にした文書: 通信は `m2-dongle-protocol.md`（根拠の記号 S1〜S5、R1、分からないことの番号 U-1〜U-17）、命令は `commands.md`（DC・TC・UC の番号）、読むだけの道具は `m2-dongle-reader.md`、状態と表示は `m1-watcher.md`。実物のログは、ブランチ `test/hub-2026-11-23-28` の `tests/replay/hub-2026-11-23-28/`（匿名化済み。以下「6 日分のログ」。#51 で main に入る予定）。

### 0.2 守ること

- **D-13 は変えない。** `commands.md` の一覧にない命令は送らない。既定で送ってよいのは、オーナーが実機で確かめ、その記録を一覧に書いた命令だけ。確かめる前の命令を送るコードは、ふつうに配る実行ファイルに入れない。オーナーが確かめるときだけ、組み立ての切り替えを入れた「試し用」の実行ファイルで、実行のたびに明示して送る（D-45、PRD の 11 章。3.1）。
- ペアリングと地図の書き込みにあたる命令は、利用者がその操作を始めたときにだけ送る。ファームウェア、フラッシュ、工場出荷に戻す命令、ドングルやトラッカーを再起動させる命令は、通し版でも禁止のまま（組み立てる関数を作らない）。
- 判定（解読、状態、調停、キャリブレーションの計算）は、入出力から分けて、Linux でテストできる形にする（AGENTS.md）。実機と再生で、同じコードが動く（`m2-dongle-reader.md` の 3 章の形を引き継ぐ）。
- 個人の情報: シリアル番号、無線のアドレス、Wi-Fi の名前とパスワード、PC の名前、利用者のフォルダー名、SteamVR の universe id を、OpenUT のログと画面に出さない（PRD の 11 章、L-1）。SteamVR に渡すトラッカーの名前の扱いは 1.5。

## 1. 全体の形

### 1.1 プロセス

```
 トラッカー ×N ──(無線)── ドングル ──(USB HID)──┐
                                               ▼
 ┌─ openut.exe（アプリ。利用者が起動する）────────────────────────────┐
 │  ドングル層: 読む（openut-dongle）、送る（openut-command の報告だけ） │
 │  調停役（openut-runtime。純粋）: 追跡の開始、Wi-Fi 情報、ペアリング、 │
 │                                 地図の作成の手順                      │
 │  空間（openut-space。純粋）: 姿勢の変換、キャリブレーションの計算     │
 │  状態と表示（openut-core。純粋）: トラッカーの状態、画面の中身        │
 │  SteamVR の客（OpenVR のクライアント API）: VR の中の板、HMD と        │
 │                 コントローラーの姿勢、SteamVR の空間の変化            │
 │  画面（窓、トレイ）、設定とファイル                                   │
 └───────────────┬────────────────────────────────────────────────┘
                 │ 127.0.0.1 の UDP（台の一覧、姿勢。openut-bridge の形）
                 ▼
 ┌─ vrserver.exe（SteamVR）─────────────────────────┐
 │  driver_openut.dll（openut-driver。薄い口）        │→ トラッカーとして登録し、姿勢を渡す
 └──────────────────────────────────────────────────┘
```

- **ドングルを持つのは、アプリ（`openut.exe`）の 1 つだけ。** 調停、姿勢の変換、キャリブレーション、状態、画面は、すべてアプリの中にある。
- **SteamVR のドライバー（`driver_openut.dll`）は、受け取った姿勢を SteamVR に渡すだけ**にする。判断を持たない。アプリが動いていなければ、台を足さない（足した台は「つながっていない」にする）。
- VIVE Hub も同じ分け方をしている（トラッカー用サーバーと SteamVR のドライバーを、名前付きパイプでつなぐ。`overview.md` の 3 章、S3 `driver-pipes.md`）。外のプロセスから姿勢を受け取る薄いドライバーには、先行事例がある（1.3）。

ドライバーを薄くする理由:

1. ドライバーは SteamVR のプロセス（`vrserver.exe`）の中で動く。ドライバーが落ちると SteamVR ごと落ちる。判断と通信をアプリに置けば、アプリが落ちても SteamVR は動き続け、台が「つながっていない」になるだけで済む。
2. ドライバーの側で `unsafe` が要るのは、SteamVR の C++ の口だけ（1.3）。その範囲を、ドライバーの 1 つのモジュールに閉じ込められる（アプリの側の `unsafe` は、OpenVR の客の 1 つのモジュールだけ。1.3.3）。
3. 判断はアプリの純粋な部品にあるので、SteamVR なしで、再生テストで確かめられる。
4. アプリを入れ替えて起動し直すとき、SteamVR を起動し直さなくてよい。

### 1.2 アプリの中のスレッド

`m2-dongle-reader.md` の 10 章の 2 本（読み取りのスレッドと主のスレッド）に、2 本を足す。

| スレッド | すること | 時計 |
|---|---|---|
| 読み取り | ドングルの入力レポートを読み、受け取った時刻を付けて流す（M2 のまま） | 読む（このスレッドだけ。D-33） |
| 主（調停） | 流れを順に処理する: 記録を書く、解読、トラッカーの状態表、調停役（K4 から）、姿勢の変換、送り口へ渡す、状態の写しを作る | 読まない（流れの時刻だけ） |
| SteamVR の客 | SteamVR につながる・離れる、VR の中の板、SteamVR のイベント（空間の変化）、キャリブレーションのあいだの HMD とコントローラーの姿勢 | キャリブレーションの見本の時刻を読む（4.3） |
| 画面 | 窓とトレイ（`eframe`、`tray-icon`。`m1-watcher.md` の 13 章）。Windows では主の実行スレッドで回す | 読まない |

- スレッドのあいだは `std::sync::mpsc` でつなぐ（`m1-watcher.md` の 2 章と同じ。非同期のランタイムは使わない）。
- 送り口（UDP）は主のスレッドから直接書く。1 回の送信は 100 バイトほどで、ふさがらない書き方（`set_nonblocking`）にする。あふれたら捨てる（次の姿勢で上書きされるので、ためない）。
- ドングルへの送信（K4 から）をどのスレッドから行うか（読み取りと同じハンドルを使えるか）は、K4 の設計で決める（未確認。hidapi の `HidDevice` を 2 つのスレッドで使えるか、同じ機器を 2 回開けるか）。

#### 1.3.2 作り方の候補と、選んだもの

| 案 | 中身 | 良い点 | 悪い点 |
|---|---|---|---|
| **A（選ぶ）Rust だけで、口の層を自前で書く** | `openut-driver` を `cdylib` にし、使う 6 つの口の関数の表と、`DriverPose_t` などの構造体を、ヘッダーから自分で書き写した宣言で持つ。`HmdDriverFactory` を Rust から出す | C++ のコンパイラーも libclang も要らない。言語が 1 つ。使う口が少ない（関数は 20 ほど） | 表の順と構造体の並びを、人が正しく写す必要がある。誤ると SteamVR が落ちうる（K2 の確かめで分かる） |
| B Rust と、`cc` で組み立てる薄い C++ | C++ の小さなファイルが、ヘッダーのクラスを継いで口を作り、Rust の関数を呼ぶ。ALVR（`alvr/server_openvr`、MIT）と utk-steamvr（MIT OR Apache-2.0）がこの形 | 表の形はコンパイラーが保証する | C++ のコードとヘッダー（BSD 3 条項）をレポジトリに入れる。Windows の組み立てに MSVC が要る。C++ の部分は `cargo fmt`・`clippy` で調べられない。「Rust で作る」（D-17）から外れる部分ができる |
| C ドライバーは C++ で書き、Rust のアプリと通信する | VMT（MIT。C++ のドライバーと、OSC の UDP）、SlimeVR-OpenVR-Driver（MIT OR Apache-2.0。名前付きパイプ）がこの形 | Rust に `unsafe` が要らない | ドライバーが Rust でなくなる（D-17 から外れる） |
| D 既にあるクレート | crates.io に、ドライバーを書くためのクレートはない（`openvr_driver`、`openvr_driver_sys`、`ovr_driver` などは「ない」）。GitHub の SpookySkeletons/openvr-driver-rs（MIT OR Apache-2.0、0.1.0、OpenVR 2.7.1、bindgen）は、crates.io に出ておらず、README に「作りかけ」、最後の更新が 2025-08 | — | 保守されていない。依存にしない |

**A を選ぶ。** 理由: (1) 言語を Rust だけにでき（D-17）、組み立てに C++ の道具が要らない。(2) ドライバーは、受け取った姿勢を渡すだけなので（1.1）、使う関数が少ない。(3) 構造体を値で返す関数（MSVC の x64 で、隠れた引数の扱いがほかと違う。この規則は Microsoft の文書を読めず未確認）は `GetPose` だけで、それは呼ばれない（ヘッダー）。ほかの関数は、引数と戻り値が数とポインターだけなので、x64 の Windows のふつうの呼び方（`extern "C"`。x64 では C++ のメンバー関数も、`this` を最初の引数にした同じ呼び方）で合う。(4) `TrackedDevicePoseUpdated` には、構造体の大きさを渡す引数がある。大きさを写し違えても、SteamVR が受け付けない見込みが高い（未確認）。

- 宣言は、OpenVR 2.15.6 の `openvr_driver.h`（BSD 3 条項の形）から、使う分だけを書き写す。書き写した宣言の元のライセンスの表示を、クレートに置く（`crates/openut-driver/LICENSE-openvr`）。ほかの人のクレートのコードは写さない。
- **B への切り替え**: K2 の確かめで、口の層の誤りが直せないと分かったら、B に替える案を `role:pm` で出す。口の層の外（台の表、包みの受け取り、姿勢の組み立て）は、A と B で同じものを使えるように、口の層を 1 つのモジュールに閉じる（1.3.3）。

**SteamVR の客（アプリの側）**: アプリは、ふつうの OpenVR のクライアントとして SteamVR につなぐ（VR の中の板、HMD とコントローラーの姿勢、イベント）。こちらには Valve の C の平らな口がある（`openvr_capi.h`。関数の表を `VR_GetGenericInterface("FnTable:…")` で受け取る形）。

| 候補 | 版・ライセンス・保守 | 使えるか |
|---|---|---|
| `openvr` | 0.9.0（2026-04-27）、MIT、「passively-maintained」の印 | 姿勢、イベント（801 を含む）、オーバーレイはある。**ダッシュボードの板（`CreateDashboardOverlay`）と `IVRChaperoneSetup` の包みがない**。`init` は `unsafe fn` |
| `openvr_sys` | 2.1.4（2026-04-27）、MIT。OpenVR 2.15.6 を包む | 2.15.6 のすべての関数の表がある（bindgen が作るので、表の形は正しい）。組み立てに CMake、C++ のコンパイラー（MSVC）、libclang が要る |
| `ovr_overlay` | 0.0.0（2022）、MIT/Apache。最後の更新が 2023-08 | 保守されていない |
| `openvr-rs` | GPL-3.0 | ライセンスが合わない |

**`openvr_sys` を直接使い、アプリの 1 つのモジュール（`src/steamvr/ffi.rs`）で包む。** ダッシュボードの板とイベントと姿勢が要り、`openvr` の包みでは足りないため。`openvr_sys` を CI の Windows で組み立てられるかは未確認（D-23 の「確かめていないこと」と同じ）。組み立てられなければ、D-23 の代案（`libloading` で `openvr_api.dll` を読み、使う関数の表だけを自前で宣言する）に替える。どちらにするかは、K3-2 の最初に決めて、PR の説明に書く。これは M1-12（SteamVR の中の通知）と同じ客なので、M1-12 は K3-2 の板に合わせる（6 章）。

#### 1.3.3 `unsafe` の範囲

ワークスペースは `unsafe_code = "deny"`。`unsafe` を許すのは、次の 2 つのモジュールだけにする（`#[allow(unsafe_code)]` を、そのモジュールの宣言にだけ付ける）。

| 場所 | 中身 | 決まり |
|---|---|---|
| `crates/openut-driver/src/abi/` | `HmdDriverFactory` の書き出し（`#[unsafe(no_mangle)]`。edition 2024 では、この属性も `unsafe_code` の対象）、関数の表、SteamVR の口の呼び出し、ポインターの読み書き | 外に出すのは安全な関数だけ（例: `Host::add_tracker(slot) -> bool`〔`TrackedDeviceAdded` の受け付けの成否。SteamVR の台の番号は返らない。1.3.4〕、`Host::update_pose(ObjectId, &Pose)`〔`ObjectId` は `Activate` で受けた番号からしか作れない〕、`log(&str)`）。SteamVR から呼ばれる関数は、すべて本体を `std::panic::catch_unwind` で包み、`panic` したら SteamVR のログに書いて、害のない値を返す（`extern "C"` の関数で `panic` が外に出ると、SteamVR ごと止まるため）。`panic = "abort"` の設定にしない |
| `src/steamvr/ffi.rs`（アプリ） | OpenVR のクライアントの初期化、関数の表の呼び出し | 外に出すのは安全な関数だけ。SteamVR がないときは誤りを返す |

- どちらの `unsafe` のかたまりにも、なぜ安全かのコメント（`// SAFETY:`）を書く。PR の説明に、`unsafe` の範囲と理由を書く（AGENTS.md）。
- レビュー担当は、この 2 つ以外に `allow(unsafe_code)` がないことを見る。`openut-driver` には、それを確かめるテスト（`src/` の下で `unsafe` の語が出るのが、`abi/` の下のファイルと、`mod abi` を宣言する 1 行だけ）を置く。

#### 1.3.4 台を足してから姿勢を渡すまでの順序

OpenVR 2.15.6 の `openvr_driver.h`（`IVRServerDriverHost::TrackedDeviceAdded`、`ITrackedDeviceServerDriver::Activate`・`Deactivate` の注）と DD（「IVRServerDriverHost」「ITrackedDeviceServerDriver」）で、2026-11-28 に確かめた決まり:

- `TrackedDeviceAdded(名前, 種類, 台のオブジェクト)` が返すのは、**受け付けたかどうか**（`bool`）だけ。`true` なら、SteamVR が、そのあとで台のオブジェクトの `Activate(unObjectId)` を呼ぶ。SteamVR の台の番号（`unObjectId`）は、`Activate` で初めて分かる。`true` でも、有効になる保証はない。`false` になるのは、名前が正しくない、同じ名前の台がもうある、などのとき（DD）。
- 台は、`Activate` が呼ばれるまで、SteamVR の口を呼ばない（DD）。`TrackedDevicePoseUpdated` も性質の書き込みも、台の番号が要るので、`Activate` のあとでしかできない。
- `Deactivate` から戻ったあとは、その台のために SteamVR の口を呼ばない（DD）。`Cleanup` は、足したすべての台の `Deactivate` のあとに呼ばれる（DD）。
- `TrackedDeviceAdded` に渡した台のオブジェクトは、`IServerTrackedDeviceProvider::Cleanup` が呼ばれるまで、有効なままにする（DD）。
- `Activate` が `TrackedDeviceAdded` の呼び出しの中で呼ばれるのか、あとのフレームで（別のスレッドから）呼ばれるのかは、ヘッダーにも DD にも書かれていない（未確認）。**どちらでも同じに動く作りにする。**

OpenUT のドライバーの台の表は、名前ごとに 1 行を持ち、次の状態を移る:

| 状態 | 入る時 | その台の姿勢を受けたら |
|---|---|---|
| 未登録 | 台の一覧で、初めてその名前を見た | 最後の 1 つだけを持っておく。次の `RunFrame` で `TrackedDeviceAdded` を呼ぶ |
| 有効化待ち | `TrackedDeviceAdded` が `true` を返した | 最後の 1 つだけを持っておく。SteamVR には渡さない |
| 有効（番号 n） | `Activate(n)` を受けた | 番号 n で渡す。途切れ（1.4.1）の判定も、この状態でだけ行う |
| 断られた | `TrackedDeviceAdded` が `false` を返した。または、`Activate` の中で誤りが起きて、誤りの値を返した | 渡さずに数える。SteamVR が起動しているあいだは足し直さない（同じ名前は、もう使えない見込みのため）。SteamVR のログに 1 回だけ書く |
| 無効 | `Deactivate` を受けた | 渡さずに数える（遅れて届いた包みも）。「正しくない」「つながっていない」も渡さない。足し直さない。`Activate` がまた来たら（ふつうは起きない見込み）、新しい番号で「有効」に戻し、ログに書く |

- **`Activate` と `Deactivate` は、出来事として列に積む。** 口の層は、`Activate(n)` を受けたら、その台の性質を書き込み（1.3.1、実装計画の K2-2 の (e)）、「台 k が番号 n で有効になった」を列（`std::sync::mpsc`）に積んで、すぐ戻る。`Deactivate` も同じに「台 k が無効になった」を積む。台の表は、`RunFrame` の初めに列を読んで、状態を移す。こうすれば、`Activate` が `TrackedDeviceAdded` の中から呼ばれても（台の表の鍵を持ったまま、もう一度台の表に入ることにならない）、あとのフレームで別のスレッドから呼ばれても、同じに動く。**台の表の鍵を持ったまま、SteamVR の口を呼ばない。**
- **`RunFrame` の 1 回の順**: (1) 列を読む（有効、無効） → (2) 受け取りのスレッドがためた包みを、台の表に入れる → (3) 台の表が返した「すること」（足す、姿勢を渡す、正しくないにする、つながっていないにする）を、鍵を離してから行う。足した台の `Activate` が効くのは、早くても次の `RunFrame` の (1)。1 フレーム（10 ms ほど）遅れるだけなので、分けない。
- **有効になったときの最初の姿勢**: 有効化待ちのあいだに持っておいた姿勢が、途切れの時間（1.4.1 の 0.5 秒）より新しければ、それを渡す。古いか、ないときは、「正しくない」を 1 つ渡す。
- **台のオブジェクトの持ち方**: 台のオブジェクトは、プロバイダーが持つ入れ物（最大 8 つ。1.4.1）に、1 つずつ `Box` に入れて置き、置いたあとは動かさない。**`Cleanup` まで解放しない**（無効になったあとも、断られたあとも、`session` が変わったあとも）。`Cleanup` で、受け取りのスレッドを止めてから、すべてを解放する。
- `session` が変わっても（1.4.1）、同じ名前の台は、同じ行（同じ状態、同じ番号）を使い続ける。断られた台と無効の台は、そのまま。

### 1.4 アプリとドライバーのあいだ（`openut-bridge`）

**127.0.0.1 の UDP で、アプリからドライバーへ一方向に送る。** 標準ライブラリ（`std::net::UdpSocket`）だけで書け、`unsafe` も外のクレートも要らない。Linux でもテストできる。先行事例の VMT（1.3.2）も、外のアプリから UDP（OSC）で姿勢を受け取る。

- ドライバーは、`127.0.0.1:<port>` にだけ結び付ける（既定のポートは 1.4.2。設定で変えられる。ドライバーの設定は `resources/settings/default.vrsettings`、アプリの設定は `config.toml` の `[bridge]`）。送り主が 127.0.0.1 でない包みは捨てる。
- 包みは、先頭の印（4 バイト）と版で見分ける。知らない版、長さの合わない包み、範囲の外の値（NaN、無限大、大きさが 1 から遠い向き）は、数えて捨てる。ドライバーは、どんな包みを受けても `panic` しない（1.3.3）。
- 名前付きパイプにしない理由: Windows の名前付きパイプを標準ライブラリだけでは作れず、`interprocess`（2.4.10、0BSD OR Apache-2.0、2026-11-25 に更新）などの依存が要る。UDP は、つなぎ直しの手順も要らない（アプリが起動し直しても、ドライバーはそのまま次の包みを受ける）。
- ほかのプログラムが同じポートへ偽の姿勢を送れる。同じ PC の中の話で、送れるのはトラッカーの姿勢だけなので、通し版では受け入れる（印と版、アプリが起動ごとに選ぶ番号〔`session`〕で、取り違えだけを防ぐ）。

#### 1.4.1 包みの形（版 1）

数はすべてリトルエンディアン。浮動小数点は 32 ビット。

| 欄 | 大きさ | 中身 |
|---|---|---|
| `magic` | 4 | `OUTB` の 4 文字 |
| `version` | 2 | 1 |
| `kind` | 1 | 1 = 台の一覧、2 = 姿勢 |
| `flags` | 1 | 0（いまは使わない。0 でなければ捨てる） |
| `session` | 4 | アプリが起動のたびに選ぶ番号（0 以外） |
| `seq` | 4 | アプリが送るたびに 1 ずつ増やす番号 |
| 中身 | 残り | 下の表 |

**台の一覧**（`kind = 1`。1 秒ごとと、台が増えたときに送る）: 台の数（1 バイト、最大 8）、続けて台ごとに、台の番号（1 バイト。0〜7。そのセッションのあいだ変えない）、SteamVR に渡す名前の長さ（1 バイト、最大 32）と名前（ASCII。1.5）。

**姿勢**（`kind = 2`。ドングルから姿勢を受け取るたびに、その台の分を 1 つ送る）:

| 欄 | 大きさ | 中身 |
|---|---|---|
| `device` | 1 | 台の番号（台の一覧の番号） |
| `state` | 1 | 0 = 位置も向きも正しい、1 = 向きだけ正しい（位置は前の値のまま）、2 = 正しくない |
| `age_us` | 4 | アプリが姿勢を受け取ってから送るまでの時間（マイクロ秒） |
| `position` | 12 | 位置 x, y, z（メートル。SteamVR の空間。キャリブレーションを当てたあと） |
| `rotation` | 16 | 向き w, x, y, z（大きさ 1 の四元数。同じ空間） |
| `velocity` | 12 | 速度（メートル毎秒。同じ空間。分からなければ 0） |
| `angular_velocity` | 12 | 角速度（ラジアン毎秒。空間は 1.3 の口の決まりに合わせる。分からなければ 0） |

- ドライバーは、同じ `session` の包みだけを使う。`session` が変わったら（アプリが起動し直した）、新しい台の一覧を待ち、名前が同じ台は、同じ SteamVR の台として使い続ける（SteamVR は台を消せないため。1.3）。
- ドライバーは、`seq` が前より小さい姿勢を捨てる（順の入れ替わり）。
- **途切れ**: ドライバーは、ある台の姿勢が 0.5 秒（`bridge.timeout_ms`。仮）届かなければ、その台を「正しくない」にして SteamVR に渡す。台の一覧が 3 秒届かなければ、全台を「つながっていない」にする。値の決め方は 8 章の仮の値の表。

#### 1.4.2 ポート

既定は 27316（仮。登録済みのよく使われるポートと重ならない数として選んだが、オーナーの PC で空いているかは未確認）。アプリが送り先を開けなかったときと、ドライバーが結び付けられなかったときは、その旨をそれぞれのログに書き、ドライバーは 10 秒ごとに結び付け直す。

### 1.5 SteamVR に渡す名前と、台の扱い

- SteamVR の台は、名前（シリアル番号の欄。`Prop_SerialNumber_String`）で見分けられ、SteamVR の「トラッカーの管理」の役割（腰、足など）も、この名前に結び付いて保存される。R-3（役割はトラッカーごとに固定）のために、**名前は、同じトラッカーなら起動をまたいで同じ**にする。
- **K4 から**: トラッカーのシリアル番号を使い、`OpenUT-<シリアル番号>` にする。VIVE Hub のドライバーの台と重ならないように、前に `OpenUT-` を付ける。シリアル番号は、利用者の PC の SteamVR の設定とログにだけ残る（D-43）。OpenUT のログには出さない。画面では、W-12 の示し方（シリアル番号の末尾）にする。利用者が SteamVR のログを人に渡すときのために、匿名化の道具がこの名前を置き換えられるようにする（9.1、実装計画の K2-5）。
- **K2・K3（VIVE Hub が追跡を始めたあとに読む）**: シリアル番号の知らせ（`NADS`）は、つながったときにしか届かない見込みで（`m2-dongle-protocol.md` の 4.5、U-6）、途中から読むと分からない。そのあいだは、ドングルの枠の番号で `OpenUT-slot<枠>` とする（U-4 で、枠の番号の読み方が正しいと分かってから）。K4 で名前が変わるので、役割は付け直しになる（粗い版として受け入れる）。
- 台の種類は「汎用のトラッカー」（`TrackedDeviceClass_GenericTracker`）。見た目の模型と入力の定義は、実装計画の K2-2。

### 1.6 姿勢の流れ

```
ドングルの姿勢（地図の座標。m2-dongle-protocol.md の 4.4）
  → 軸の並べ替え（openut-space::AxisMap。U-14 で決める）
  → キャリブレーションの変換（openut-space::Calibration。4 章。なければ そのまま）
  → トラッカー自身の向きの直し（向きだけ。openut-space::AxisMap の N。4.3.4。既定は何もしない）
  → 追跡の状態で、正しさを決める（下の表）
  → 送り口（1.4）→ ドライバー → SteamVR
```

| ドングルの追跡の状態 | 送る `state` | 位置 | 向き |
|---|---|---|---|
| 2 追跡中 | 0 | そのまま | そのまま |
| 3 喪失（向きだけ有効）、4 直前に喪失 | 1 | その台の最後の「追跡中」の位置のまま | そのまま |
| それ以外、または「追跡中」を一度も受けていない | 2 | — | — |

- 3 と 4 で位置を止めるのは、R-5（喪失中は最後の正しい位置を保ち、回転だけ更新する）の最も粗い形。飛びの検出、暴走の検知（R-6）は、通し版のあと。
- 速度と角速度は、ドングルの姿勢の値（`m2-dongle-protocol.md` の 4.4。意味は未確認）を使わず、通し版では 0 を送る。SteamVR の先読みが効かないぶん遅れて見えるかを K2 で見て、要れば、続く 2 つの姿勢の差から作る（次の PR）。

### 1.8 オーナーへの渡し方

- 実行ファイルは、main の成果物として GitHub Actions が組み立てる（PR #58。`openut-windows-x64`）。K2 からは、ドライバーのフォルダー（1.3.1 の形）も成果物に入れる。ワークフローは PM のもの（`.github/`）で、K2-2 が main に入る前に PM が直す（D-43）。
- ドライバーの登録は、SteamVR の `vrpathreg`（1.3.1）で行う。アプリに `openut driver register` と `openut driver unregister` を作り、オーナーが手で打つ命令を減らす。登録と取り消しは、SteamVR の設定のファイル（`openvrpaths.vrpath`）を書き換えるだけで、機器には何も送らない。

## 2. VIVE Hub がしていることの順序

6 日分のログの、サーバーのファイルとドライバーのファイルを時刻で合わせて読んだ（2026-11-28。設計担当）。数は 6 日分のもの。トラッカーは A〜C と呼ぶ。この章は、K4〜K6 の設計の材料で、細かい順序と待ち時間は、次の PR で調停役の設計にする。

### 2.0 読み方

- **ドライバーのファイル（`ViveTrackerDriver_*.txt`）は、SteamVR のドライバーのログではない。** トラッカー用サーバーのプロセスの中の、HID とドングルを扱う層のログ（11 回の起動のどれでも、2 つのファイルのプロセスの番号が同じで、スレッドの番号も共有している）。
- 誰が始めたかは、スレッドで分かる: VIVE Hub の画面（ペアリング、`StartTrackerSetup`、まとめての電源オフ）、地図づくりの画面（ログの `TrackerSetup`）、VR の中のキャリブレーションの画面（ログの `TrackerSetupLite`）、SteamVR のパイプ。
- PC からトラッカーへの命令は、文字列そのものではなく、効き目（「power state: 21 にした」「Wi-Fi 情報を渡した」など）の形でだけ記録される。地図の命令（`pMS_*`、`ALE`）は記録されない。命令の文字列は、`m2-dongle-protocol.md` の 6 章（S3 の取り込み）と突き合わせる。

### 2.1 追跡の開始（毎日の始まり）

| 段 | 何が起きるか（ログの関数名と本文の形） | 待つもの | かかった時間 |
|---|---|---|---|
| 0 サーバーの起動 | 設定を読む（カメラのフレームの速さ、自動スリープ）、保存したキャリブレーションを読む、Wi-Fi の国を決める（`FindCountryCode`。毎回 `JP` から `FR` へ変えている）、ドングルを見つけて起こす（`WakeupDongle`）、前のペアリングの記録を読む | ドングル | 起動から 0.3〜1.4 秒でドングルが使える |

| 2 つながる | `Tracker is paired to slot N, connected: 1`、接続の 10 秒の見張りが始まる（`Enter TrackerConnectionTimeoutProc`）、トラッカーの自己申告（`Set is host`、`Set has_map`）、`Add new tracker: (N)` | トラッカーの知らせ | 枠の行から Add まで 0.6〜4.1 秒（中央値 0.9 秒） |

### 2.4 キャリブレーション

- 回転は、218 行のすべてで鉛直の軸まわりだけ（x と z が 0）。
- **キャリブレーションのあいだ、ドライバーのファイル（HID の層）に 1 行も出ない。** 機器への命令は要らないと読める（D-40 の「確かめていないこと」への答えの材料）。
- 「空間が変わった」は、SteamVR のパイプがつながったときに、universe id をくらべて決めている（`Universe id from (X) to (Y), local's: (Z)`）。3 回とも、保存した id が 0 のとき（前の回に、SteamVR の空間の様子を読むのに失敗していた〔`Fail to parse json data.`〕）で、空間が本当に変わったのではない見込み（推測）。そのあと、VR の中に知らせを出す手伝いのプログラムが、20 秒で時間切れになっている（2 回とも）。

### 2.5 OpenUT への意味（K4〜K6 の設計で使う）

1. **役割の決め方**: ホストが動いていなければ、つながった台をホストにする。動いていれば、クライアントにする。ホストが外れたら、すぐ残りの 1 台をホストにする。VIVE Hub と同じでよい。
2. **Wi-Fi 情報**: ホストから 1 回受け取り、ホストが外れるまで持つ。クライアントの求めには、持っていればすぐ答える。持っていなければ、ホストに問い合わせ直す。ホストの状態の知らせ 1 つで、ホストの扱いを変えない（「始まらない」の 4 回の原因の見込みを避ける）。
3. **クライアントは、ホストが地図を再利用できてから地図を受け取る**ので、追跡中になるまでの時間（中央値 92 秒）は、OpenUT が早めることはできない。画面では「待機中」として、何をすればよいか（R-8）を出す。
4. **ペアリングの窓**: 毎日の始まりに要るかは、K1 の C-2 で決める。
5. **地図の作成は、始めた時点で地図を消す**ので、K6 では、確かめてから始め、取り消しても戻らないことを示す。
6. **キャリブレーションは、機器に何も送らない**（K3）。始める合図に、トラッカーのシステムボタンを使える見込みがある（ボタンの読み方は未確認。K1 で確かめる。5.2）。

## 3. 送る命令

`commands.md` の 8 章に、切れ目ごとの候補の表を足した。この章は、その考え方。

- **K1〜K3 は、何も送らない。** キャリブレーションも、機器への命令が要らない（2.4）。
- **K4 で「送る」に上げる候補**: 追跡の開始に要る「状態を変える」命令（DC-01 で運ぶ TC-02、TC-05〜TC-07、TC-09〜TC-12 と、ホストへの Wi-Fi 情報の問い合わせ〔文字列は未確認〕）。ペアリングの窓（DC-03a、DC-03c）が毎日要るなら、それも入る（2.2）。どれも、VIVE Hub が毎日送っているもので、トラッカーの電源を入れ直して VIVE Hub を起動すれば、VIVE Hub がまた送り直す（元に戻せる）。
- **K5 の候補**: DC-03a（窓を開く）、DC-03c（窓を閉じる）、DC-04（枠の状態の問い合わせ）。枠ごとの解除（DC-03e）は、利用者が「解除」を押したときだけ。
- **K6 の候補**: TC-50（どの台かを知らせる）、TC-34（地図づくりの段の合図）、TC-33（保存）。始めた時点で全台の地図が消える見込み（2.3）なので、利用者が確かめたときだけ送る。
- **通し版でも禁止のまま**: 再起動、電源を切る、工場出荷に戻す、ファームウェア、フラッシュ、識別子の書き換え、地図を消すだけの命令（TC-31）。

### 3.1 確かめる前の命令を、オーナーが初めて送るとき（D-45）

D-13 では、既定で送ってよいのは、オーナーが実機で確かめた命令だけ。確かめるには、一度は送らなければならない。その道は、**ふつうに配る実行ファイルには入れない**（D-45、PRD の 11 章。`commands.md` の 6 章の 6）。第 1 版に書いた「実行のたびの引数だけで許す」案（試しの許可）は、公開の版を落とした人がだれでも有効にできるので、採らなかった。

- **組み立ての切り替え**: 確かめる前の命令を組み立てる関数は、`openut-command` の Cargo の feature **`unverified-commands`**（既定は切）の中にだけ置く。アプリ（`openut`）は同じ名前の feature を持ち、それを `openut-command` に渡すだけにする。既定の組み立て（利用者が落とす `openut.exe`）には、その命令を組み立てるコードも、送るコードも入らない。
- **試し用の実行ファイル**: feature を入れて組み立てたものを、別の名前の成果物で渡す（名前の案は `openut-windows-x64-trial`。ワークフローは PM が直す。K4 の前に）。試し用は、起動のたびに、コンソールとログの最初の行に、試し用の版であることを書く。
- **試し用でも、実行のたびに明示する**: コマンドの引数で切れ目の名前を書いたとき（例: `openut run --try K4`）だけ、その切れ目の候補として `commands.md` の 8 章に載せた命令を送る。設定のファイルには書けない（残らない）。既定の組み立てでは、`--try` を付けると「この版には、確かめる前の命令が入っていない」と出して、何も送らずに終わる。
- **記録**: 許したこと（切れ目の名前）と、送った命令（ID、宛先の匿名の名前、時刻）を、アプリのログに書く（`commands.md` の 6 章の 4）。
- **確かめたあと**: オーナーが確かめた命令は、`commands.md` のその命令の「確かさ」に記録してから、PR で、組み立てる関数を feature の外（既定の組み立て）に移す（`commands.md` の 7 章）。
- **「禁止」の区分の命令**は、試し用にも入れない（組み立てる関数を作らない。いまの決まりのまま）。

**既定の組み立てに入っていないことの確かめ方**（D-45 の 6）。`m2-dongle-reader.md` の 4 章の「送らないことの検査」と同じく、ソースとファイルを読んで確かめる検査を、3 つ重ねる。CI の検査（`verify.sh`）は `--all-features` で動くので、feature を入れた組み立てでも切った組み立てでも同じ結果になる形にする。

1. **置き場所の検査**（`openut-command` のテスト）: 確かめる前の命令を組み立てる関数は、`crates/openut-command/src/unverified/` の下にだけある。そのモジュールを宣言するのは、`src/lib.rs` の `#[cfg(feature = "unverified-commands")]` の付いた `mod unverified;` の 1 か所だけ。`unverified/` の外で組み立てる命令の ID は、どれも `commands.md` の「確かさ」にオーナーの確認の記録があり、`unverified/` の中の ID には、どれもその記録がない（`commands.md` とソースを読んでくらべる）。
2. **Cargo の設定の検査**（同じテスト）: ワークスペースのどの `Cargo.toml` でも、`default` の feature に `unverified-commands` が入っていない（ほかの feature をたどって入るものも）。依存の宣言の `features = [...]` に、それを書いているものがない。許すのは、アプリの `[features]` の `unverified-commands = ["openut-command/unverified-commands"]` の 1 行だけ。
3. **成果物の検査**（ワークフロー。PM に頼む。K4 の前に）: `unverified/` の中に、試し用の印の文字列（例: `OPENUT-UNVERIFIED-COMMANDS-BUILD`。試し用の起動の最初の行に使うので、試し用の組み立てでは必ず残る）を置く。組み立てのあとに、既定の `openut.exe` にこの文字列がなく、試し用の `openut.exe` にあることを確かめる（試し用にあることで、検査そのものが効いていると分かる）。

モジュールの中の並び、`--try` の読み方、印の文字列は、K4 の項目で決める。K1〜K3 は何も送らないので、この決まりが効くのは K4 から。

ペアリングと地図の書き込み（K5、K6）の命令は、いまは「禁止・消す／書く」の区分で、組み立てる関数がない。これを「利用者の操作のときだけ送る」区分に移す案は、K5・K6 の設計の PR で出し、PM とオーナーの了承を得る（`commands.md` の 8 章の終わり）。

## 4. スペースキャリブレーション

### 4.1 何を求めるか

トラッカーの姿勢は、トラッカーの地図の座標で届く（`m2-dongle-protocol.md` の 4.4。原点と向きは U-14）。HMD とコントローラーの姿勢は、SteamVR の空間にある。**地図の座標から SteamVR の空間への変換を 1 つ求め**、すべてのトラッカーの姿勢に当てる（地図は全台で共有されるので、変換も 1 つでよい。PRD の 9 章）。

- 当てる先の空間は、SteamVR の「生の空間」（`TrackingUniverseRawAndUncalibrated`。ドライバーが渡す姿勢と同じ空間。1.3.1 の「HMD の姿勢」）にする。プレイエリアの原点（立った位置の原点）への変換は、SteamVR がする。
- 変換の形: **鉛直の軸まわりの回転（θ）、移動（t）、大きさの倍率（s）**。地図の点 p を `s·Ry(θ)·p + t` に、向き q を `Ry(θ)·q` に移す（倍率は向きに効かない）。
- 形をこう決めた根拠は、VIVE Hub のログ（4.2）。VIVE Hub が当てている変換は、6 日分のどれも、回転が鉛直の軸まわりだけで、倍率を持つ。どちらの空間も重力で上下が決まっているので、傾きは求めなくてよい。

### 4.2 VIVE Hub のログから分かること

6 日分のログのサーバーのファイルの行（関数名と本文の形。数は 2 章の数え方）:

1. VR の中の VIVE Hub のアプリ（ログの `SystemApp`）から「始める」が届く（`ParseCommandFromSystemApp` の `Notify start space calibration`）。
2. サーバーは変換を消し（`Space calibration is reset.`）、恒等の変換をトラッカーごとに当てる（`Tracker::SetSpaceCalibrationInfo` の `Transform - rotation:(0, 0, 0, 1 w), pos:(0, 0, 0), scale: 1`）。状態は `Cali status: 0`。
3. 10 秒ほどのち、VR の中のアプリから変換が届く（`Submit space calibration transform`）。サーバーは、そのときの SteamVR の空間の様子（`GetCurrentSteamVRChaperoneInfoAndStore` の `Trans in chaperone`、`Chaperone center to bound`、`current universe id`）と、地図を作った時刻を、変換と一緒にファイルに保存し、トラッカーごとに当てる。状態は `Cali status: 1`。数秒あとに、倍率だけが違う変換がもう一度届くことがある（例: 11/24 23:37:51 に倍率 1.000、23:37:55 に 0.963）。
4. 起動のときに、保存したファイルを読む（`ReadCalibratedDataFromFile` の `Succeed to read calibrated json.`）。
5. SteamVR の空間が変わったと見ると、やり直しを促す（`UpdateSpaceCalibrationWithNewChaperone` の `Previous space is changed, notify user to redo space calibration.` と `Show redo calibration.`）。

ここから言えること（推測を含む）:

- **変換の計算は、VR の中のアプリがしていて、サーバーは受け取って当てるだけ**（3 の形から。推測）。OpenUT では、計算もアプリ（`openut.exe`）の中で行う。
- 変換は、地図に結び付く（地図を作った時刻と一緒に保存している）。地図を作り直したら、キャリブレーションもやり直す（K6）。
- 何と何を突き合わせているか（コントローラーか、HMD か、どう動かすか）は、ログからは分からない。

### 4.3 OpenUT のやり方

**トラッカー 1 台とコントローラー 1 本を、片手で重ねて持ち、ゆっくり動かして回す。** 2 つの姿勢の動きを突き合わせて、変換を求める。先行事例（4.7）と同じ考え方（2 つの機器を一緒に動かし、回転を先に、移動をあとに解く）で、計算の手順は下に自分の言葉で書く（先行事例のコードは写さない）。

**操作の流れ（何をいつ見せるか。見た目と文言は UI/UX デザイン担当）**:

1. 利用者が、SteamVR のダッシュボードの OpenUT の板で「キャリブレーション」を押す（コントローラーのレーザーで押す）。HMD を外さずにできる（R-4）。
2. 板が手引きを出す: トラッカー 1 台とコントローラーを重ねて片手で持つ。ずれないように持ったまま、ゆっくり 8 の字を描き、手首をいろいろな向きに回す。
3. アプリが見本を集める（最大 20 秒）。板に、進み具合（回した向きの広がり。4.3.3 の (4)）を出す。
4. 足りたら計算する。良ければ、すぐ当てて保存し、板に「終わり」を出す。悪ければ、理由（もっと回す、重ねた持ち方がずれた）を出して、2 に戻る。利用者は、いつでも「やめる」を押せる（前の変換に戻す）。
5. 利用者がダッシュボードを閉じる。

- どのトラッカーと、どのコントローラーを使ったかは、利用者に選ばせない。動きがいちばんそろっている組を、アプリが選ぶ（4.3.2）。

#### 4.3.1 見本の集め方

- SteamVR の客のスレッドが、キャリブレーションのあいだだけ、30 回毎秒（仮）、全機器の姿勢を生の空間で読む（OpenVR のクライアント API の `GetDeviceToAbsoluteTrackingPose`。予測の時間は 0）。読んだ時刻（`Instant`）を付けて、主のスレッドへ渡す。コントローラーで、姿勢が正しいもの（`bPoseIsValid` で、追跡の結果が「動いている・正常」）だけを使う。
- 主のスレッドは、トラッカーの姿勢（軸の並べ替えのあと、キャリブレーションの前）を、受け取った時刻つきで、計算の部品（`openut-space::calib::Collector`）に渡す。追跡の状態が 2（追跡中）のものだけ。
- 計算の部品は、時刻を引数で受ける（時計を読まない）。2 つの機器の時刻は、どちらもアプリの同じ単調な時計で付ける。

#### 4.3.2 組と時刻のずれの選び方

- トラッカーの姿勢は、無線と処理のぶん、コントローラーより遅れて届く見込み（量は未確認）。そこで、**角速度の大きさの並びどうしの相関**を、時刻のずれ δ を −150〜+150 ms（5 ms きざみ。仮）で動かして求め、いちばん高い δ を使う。
- 同じ計算を、すべての（トラッカー、コントローラー）の組で行い、相関がいちばん高い組を使う。相関が 0.8（仮）より低ければ、「重ねて動かしていない」として失敗にする。
- トラッカーの姿勢は、コントローラーの見本の時刻 − δ に、前後の 2 つから線形に（向きは球面線形に）補う。前後の間が 50 ms（仮）より空いていれば、その見本は捨てる。

#### 4.3.3 計算

i 番目の見本の、コントローラーの姿勢を (Rc_i, pc_i)（生の空間）、トラッカーの姿勢を (Rt_i, pt_i)（地図の座標）とする。重ねて持っているので、2 つのあいだは固い。

- 向き: `Rc_i = Ry(θ)·Rt_i·Q`（Q は、トラッカーから見たコントローラーの向き。一定）
- 位置: `pc_i = s·Ry(θ)·(pt_i + Rt_i·d) + t`（d は、トラッカーから見たコントローラーの位置。一定）

(1) **θ を求める**: 十分に離れた 2 つの見本 i と j（向きの差が 15° 以上。仮）の組ごとに、空間の側から見た回転の差 `ΔC = Rc_j·Rc_iᵀ`、`ΔT = Rt_j·Rt_iᵀ` を作る。Q が消えて `ΔC = Ry(θ)·ΔT·Ry(θ)ᵀ` になるので、2 つの回転の軸 a_C と a_T は `a_C = Ry(θ)·a_T` を満たす。軸を水平面に写した 2 次元のベクトルどうしの向きの差を、回転の角の大きさで重みを付けて平均する（2 次元の最小二乗の回転。閉じた式で解ける）。

(2) **s、t、d を求める**: θ が決まれば、位置の式は、未知数 s、t（3 つ）、e = s·d（3 つ）の 7 つについて 1 次になる: `pc_i = s·(Ry·pt_i) + (Ry·Rt_i)·e + t`。見本 1 つで式が 3 本できるので、最小二乗で解く（7×7 の正規方程式を、部分的な軸の入れ替えつきの消去法で解く）。

(3) **良し悪し**: 次のどれかに当たれば失敗にする（値はすべて仮。8 章）。
   - 正規方程式がほぼ解けない（消去法の軸の大きさが、いちばん大きいものの 1e-6 倍より小さい）。回し方が足りない。
   - 位置の残りの差の二乗平均が 2 cm を超える。持ち方がずれたか、時刻のずれが合っていない。
   - θ を当てたあとの `(Ry·Rt_i)ᵀ·Rc_i`（= Q のはず）のばらつきが 3° を超える。
   - 軸の上下が合わない: ΔC と ΔT の軸の鉛直の成分の差の平均が 0.1 を超える（軸の並べ替え〔4.3.4〕が合っていない）。
   - 倍率が 0.9〜1.1 の外。

(4) **見本が足りたか**: トラッカーの向きが、初めの見本から、2 つ以上の互いに離れた軸（なす角 45° 以上。仮）のまわりに、それぞれ 30° 以上（仮）回ったら、計算を試す。20 秒たっても足りなければ、失敗（もっと回す）。

(5) 倍率は、VIVE Hub と同じく求める（4.2 の 3）。`calibration.fix_scale = true` で 1 に固定できる（そのとき未知数は 6 つ）。

#### 4.3.4 軸の並べ替えも、キャリブレーションで決める

ドングルの姿勢の軸の向き（どれが上か、右手系か）は、まだ分からない（U-14）。軸の並べ替え（`AxisMap`）は、軸の入れ替えと符号の組み合わせ（48 通り）のどれか、という見込みで作る。並べ替えの行列を M とすると、位置は `M·p`、向きの行列は `M·R·Mᵀ`。SteamVR の空間は、右手系で +y が上（`openvr_driver.h` と `openvr.h` の先頭の注）なので、Ry は y の軸まわりの回転。

**鉛直の軸まわりに 90° ずつ違う 4 つの並べ替えは、見分けられない**（第 1 版へのレビューの指摘）。並べ替え M と θ を当てると、位置は `s·Ry(θ)·M·p + t`、向きは `Ry(θ)·M·R·Mᵀ` になる。M の代わりに M' = Ry(φ)·M（φ は 90°、180°、270°。このときの Ry(φ) も符号つきの入れ替えなので、M' も 48 通りの 1 つ）を使い、θ' = θ − φ とすると、位置はまったく同じになる。向きは `Ry(θ)·M·R·Mᵀ·Ry(φ)ᵀ` になり、右から一定の回転が掛かるだけ。4.3.3 の式では、トラッカーから見たコントローラーの向き Q と位置 d を、Q' = Ry(φ)·Q、d' = Ry(φ)·d に取り直せば、見本とまったく同じに合う。だから、4 つの残りの差は、雑音があっても同じになる（レビューの試算では、位置に 1 mm の雑音を足した見本で、4 つとも 1.6993 mm だった）。

そこで、次のように決める。

- **見分けられる組から選ぶ**: 48 通りを、「地図のどの軸（符号つき）が SteamVR の +y（上）に移るか」（6 通り）と、「行列式が +1 か −1 か」（右手系のままか、鏡に映すか。2 通り）で、12 の組に分ける。1 つの組の 4 つは、互いに鉛直の軸まわりに 90° の倍数だけ違う（M'·Mᵀ が Ry(φ) になる）。
- **M の組と −M の組は、倍率の符号でだけ分かれる**: −M の組（上の軸の符号と、行列式の符号が、どちらも逆）は、向きが M と同じ（`(−M)·R·(−M)ᵀ = M·R·Mᵀ`）で、位置は `s·Ry(θ)·(−M)·p = (−s)·Ry(θ)·M·p` なので、倍率 s の符号だけが違う。4.3.3 の (2) の最小二乗は s の符号を決めないので、2 つの組の残りの差は同じになる（設計担当の試算で確かめた。下）。倍率は正なので、**(2) で s が 0 以下になった組は、候補から外す**。
- キャリブレーションでは、**12 の組ごとに、代表の 1 つで (1) と (2) を解き**、s が正の組のうち、残りの差がいちばん小さい組を選ぶ。2 番目の組との差がはっきりしない（残りの差の比が 1.5 倍より小さい。仮）ときは、失敗（軸が合わない）にして記録に残す。選んだ組に、(3) の良し悪しを当てる。くらべるのは組どうしなので、同じ組の 4 つが 1 番目と 2 番目に並ぶことはない。`fix_scale = true`（s = 1 に固定。4.3.3 の (5)）のときは、−M の組は残りの差が大きくなるので、外さなくても分かれる。
- 試算（2026-11-28、設計担当。手で書いた数行の計算で、実装の代わりではない）: 8 の字と手首の回し（600 個の見本）、位置に 1 mm の雑音、θ = 37°、s = 0.98 で、見本を作る並べ替えを 7 通り（上の軸と行列式を変えて）試した。同じ組の 4 つは、どれも残りの差が 1.8 mm で、θ だけが 90° ずつ違った。−M の組も 1.8 mm で、s が −0.98 になった。s が正の組だけを残すと、7 通りすべてで正しい組が選ばれ、2 番目との比は 115〜131 倍だった。
- **代表の決め方**: 組の 4 つのうち、地図の水平な 2 つの軸（上に移らない 2 つ）のうち番号の小さいほう（x、y、z の順）の + 向きを、SteamVR の +x に移すもの。例: 地図の +z が上に移る組なら、地図の +x を SteamVR の +x に移すもの（地図の y は、行列式で決まる向きで SteamVR の z に移る）。4 つの中で、この形のものは 1 つだけ。決め方が決まっているので、同じ見本からは、いつも同じ代表と θ になる。θ は −180° より大きく 180° 以下に収める。
- **保存して当てるのは、代表と θ の組み合わせ**（4.4）。位置への効き目 `Ry(θ)·M` は、見本を作った並べ替えが組の 4 つのどれであっても、同じになる。
- **トラッカー自身の向き**（トラッカーの本体のどちらを前とし、どちらを上として SteamVR に渡すか）は、**このキャリブレーションでは決まらない**（上のとおり、Q に吸われる）。そこで、計算とは別の、一定の回転 N で決める。SteamVR に渡す向きは `Ry(θ)·M·R·Mᵀ·N`。
  - N は、行列式が +1 の符号つきの入れ替え（24 通り）。設定 `space.body_rotation`（文字列の形は `AxisMap` と同じ。例: `+x+y+z`）。既定は恒等（何もしない）。行列式が −1 の文字列は断る。
  - N は位置に効かない。キャリブレーションの計算には入らない（計算は、N を当てる前の向きで行う。4.3.1）。`calibration.json` にも入れない（設定に置く）。
  - N の決め方: K1 の記録で、平らな台に置いたトラッカーの向き（5.2 の、試し C の 4）から、本体のどの軸が上を向いていたかを出す。K3 の手順 7 で、SteamVR の模型と、手の中のトラッカーの向きを見くらべてもらう（8 章）。SteamVR の汎用のトラッカーの模型の軸（どちらが前と上か）は未確認。
- K2 では、まだキャリブレーションがないので、K1 の記録（トラッカーを真上に持ち上げた動き）から、上に移る軸（符号つき）を決め、その組のうち行列式が +1 のものの代表を、既定の並べ替えにする（5 章の K1）。鏡に映すかどうかは K1 では分からないので、K2 では鏡に映さない（模型の回り方が鏡に映したように見えても、K3 で決まる）。

### 4.4 保存

- `%APPDATA%\OpenUT\calibration.json`（`m1-watcher.md` の 9.3 の場所の決まりに足す）。中身: 版、θ（四元数で）、t、s、軸の並べ替え（選んだ組の代表。4.3.4）、残りの差、見本の数、時刻のずれ δ、作った時刻（UTC）、そのときの SteamVR の空間の手がかり（4.5）。
- universe id は、個人の情報（L-1）なので、そのまま書かずに、64 ビットのハッシュ（FNV-1a。自前で数行）だけを書く。同じかどうかを見るのに使うだけなので、元に戻せなくてよい。
- アプリの起動のときに読み、すぐ当てる。読めない、版が違うときは、変換なし（地図の座標のまま）で動かし、画面と VR の中の板で「キャリブレーションが要る」を出す。
- OpenUT のログには、変換の数と残りの差を書いてよい（個人の情報を含まない）。universe id のハッシュは書かない。

### 4.5 SteamVR の空間が変わったとき

- キャリブレーションをしたときの SteamVR の空間の手がかりを保存する: HMD の universe id のハッシュ、生の空間から見た立った位置の原点（`GetRawZeroPoseToStandingAbsoluteTrackingPose`）、プレイエリアの大きさ。VIVE Hub も、似た値（`Trans in chaperone`、`Chaperone center to bound`、`current universe id`）を保存している（4.2）。
- SteamVR につながったときと、空間が変わったというイベント（1.3 のイベントの一覧）を受けたときに、いまの手がかりとくらべる。universe id が違うか、原点が 5 cm または 2° より動いていたら（仮）、**やり直しが要る**ことを、VR の中の板と画面に出す（R-4）。変換は消さずに当て続ける（何もないより近い見込み）。
- Meta Quest 3 で、境界を引き直したときや、向きを合わせ直したときに、SteamVR の生の空間そのものが動くのか、立った位置の原点だけが動くのかは、未確認（つなぎ方〔Steam Link、Quest Link、Virtual Desktop〕でも違いうる）。K3 の 8 で確かめる。

### 4.6 VIVE Hub の保存した結果を読めるか

- VIVE Hub は、結果を JSON のファイルに保存している（4.2 の 4）。場所と形は未確認。
- 読めたとしても、VIVE Hub の変換は、VIVE Hub のドライバーが地図の座標を SteamVR の向きに直したあとの座標に当てる値で、OpenUT の軸の並べ替え（4.3.4）と同じとは限らない。
- **通し版では読まない。** K3 の 15 秒の操作で済むため。代わりに、K3 で、OpenUT が求めた変換と、同じ日に VIVE Hub がログに書いた変換（`SetSpaceCalibrationInfo` の行）をくらべる。θ が 2° 以内、t が 3 cm 以内、s が 1% 以内でそろえば、VIVE Hub の座標の扱いと OpenUT のものが同じだと分かり、最初の 1 回だけ読む機能を、通し版のあとに足せる（足すかは、そのときに PM が決める。D-43 の (4)）。OpenUT の θ は、選んだ組の代表（4.3.4）に対する角なので、90° の倍数だけずれて見えることがある。そのときは、ずれの角も記録する。

## 5. 実機で確かめる順序（切れ目）

### 5.1 順序と、その理由

| 切れ目 | 中身 | 機器に送るもの | 入る項目（7 章） |
|---|---|---|---|
| **K1 読むだけ** | VIVE Hub を止めて、ドングルから状態と姿勢を読む（M2 の試し A〜D） | なし | M2-1〜M2-5 |
| **K2 SteamVR への受け渡し** | VIVE Hub が追跡を始めたトラッカーを、VIVE Hub のサーバーを止めたあと OpenUT が読み、SteamVR に渡す | なし | K2-1〜K2-4 |
| **K3 キャリブレーション** | K2 の状態で、VR の中でキャリブレーションをして、保存し、次の起動で使う | なし | K3-1〜K3-3 |
| K4 追跡の開始 | VIVE Hub を使わずに、電源を入れたトラッカーの追跡を OpenUT が始める。画面（T-6） | 状態を変える命令（3 章） | 次の PR |
| K5 ペアリング | トラッカーを OpenUT でペアリングする | ペアリングの表を書く命令（利用者の操作のときだけ） | 次の PR |
| K6 地図の作成 | 部屋の地図を OpenUT で作り直す | 地図を書く命令（利用者の操作のときだけ） | 次の PR |

**Issue #57 の案（読むだけ → 追跡の開始 → SteamVR → キャリブレーション → ペアリング → 地図）から、SteamVR とキャリブレーションを、追跡の開始より前に移した。** 理由:

1. **送らないものを先にする。** K2 と K3 は、機器に何も送らない（D-13 の決まりの外で確かめられる）。「読むだけが先、書き込みにあたるものが後」を、「送らないものが先」に広げた。
2. **壊れ方を分ける。** K2・K3 で新しく入るのは、SteamVR のドライバーの口（1.3）とキャリブレーションの計算で、どちらも機器の命令とは別の失敗をする（SteamVR が落ちる、位置がずれる）。追跡の開始と同時に試すと、うまくいかなかったときに、どこが悪いかが分からない。
3. **実装を並べて進められる。** K2 の送り口とドライバーは、M2 の実装と別のファイルなので、M2 と同時に作れる（7 章）。

**前提**: K2・K3 は、**VIVE Hub のサーバーを止めたあとも、追跡していたトラッカーから姿勢が届き続けること**（M2 の試し C の C-1。U-1 の (b)）を前提にする。C-1 で届かなかったら、Issue の案の順（K1 → K4 → K2 → K3）に戻し、K2・K3 は、K4 で OpenUT が始めた追跡で確かめる。K2・K3 の項目は、どちらの順でも同じものを作る（入力が、どちらでも同じドングルの姿勢のため）。

**どの切れ目でも共通**:

- 確かめる手順は、オーナーが 15 分以内で行える形にする。準備（成果物を落として置く、SteamVR の設定を変える）は、時間に入れず、PM が段取りする（`needs-human` の Issue）。
- 結果は、手順ごとに「できた・できなかった・見ていない」で書いてもらう。できなかったときは、画面に出た文言と時刻（分まで）を書いてもらう。
- 記録は、個人の情報を含まない形だけを渡してもらう（OpenUT のログは、もともと含まない作り。M2 の記録は `export --anonymize` を通したもの）。SteamVR のログ（`vrserver.txt`）は、シリアル番号と利用者のフォルダー名を含みうるので、OpenUT のドライバーの行（先頭が `openut:`）だけを切り出して、匿名化の道具を通してから渡す。
- 実機に命令を送るのは K4 から。K4 からは、送った命令を、ID、宛先（匿名の名前）、時刻で記録する（`commands.md` の 6 章の 4）。
