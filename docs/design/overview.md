## 1. 位置付け

OpenUT は、VIVE Hub の代わりに、VIVE Ultimate Tracker を SteamVR（Windows）で使うための PC 側のソフトウェア（D-9）。

- 日々の利用（追跡の開始、SteamVR への受け渡し）、ペアリング、部屋の地図の作成を、最終的にすべて受け持つ。
- VIVE Hub の「始まらない」不具合（PC がホストの Wi-Fi 情報を持たなくなる）を起こさない。
- トラッカーの中の SLAM のクラッシュと暴走は、ファームウェアを直さず（D-10）、PC 側で素早く見つけて、位置を止める・立て直す・知らせる。
- ファームウェアとドライバーの更新だけは、VIVE Hub のものを使う（D-11）。
- 不調のときのログを集め、匿名化して送れるようにする（D-12）。
- Windows のアプリとして、Rust で作る（D-17）。

2026-11-27 の初版にあった「地図の作成とペアリングは VIVE Hub に任せる」「見張り役の記録を見てから段階2 を決める」という前提は、D-9 でなくなった。

## 3. VIVE Hub の構成（解析メモによる）

ドングル（USB HID）とトラッカーを、`ViveTrackerServer.exe`（トラッカー用サーバー）が受け持つ。SteamVR のドライバー、設定画面、VIVE Hub 本体は、名前付きパイプでこのサーバーと話す。出典は `docs/research/findings-2026-11-27.md` の「先行事例」（vive-ultimate-linux の解析メモ）。

- M1 は、このサーバーのログ（`ViveTrackerServer_YYYYMMDD.txt`）を読むだけ。サーバー、パイプ、ドングルには何も送らない（W-7）。
- M2 以降は、このサーバーを止めて、OpenUT がドングルを直接扱う。ドングルは同時に 1 つのプログラムしか扱えない前提なので、サーバーが動いていたら起動を断る（DG-3。前提が正しいかは Issue #6 で確かめる）。

トラッカーの仕組み（`findings-2026-11-27.md` の「始まらない問題」）: 1 台がホストになって Wi-Fi の親機を立て、残りはそこにつないで地図をもらう。クライアントは接続先を PC に尋ね、PC はホストから聞いておいた SSID・パスワード・周波数を答える。

## 4. クレートの構成

Cargo のワークスペースにする。レポジトリの直下の `Cargo.toml` は、ワークスペースと、アプリのパッケージ `openut` を兼ねる。詳しい配置は `implementation-plan.md` の 1 章。

| クレート | 置き場所 | 中身 | 入出力 |
|---|---|---|---|
| `openut` | `src/`、`tests/` | アプリ（実行ファイル `openut`）。コマンド、設定、ファイルの読み書き、見張りのループ、通知、トレイ、状態の窓。再生テストと、要件とテストの対応の表（`tests/README.md`） | 持つ |
| `openut-core` | `crates/openut-core/` | 時刻、トラッカーの呼び名、出来事、状態、検出の規則、案内と配信の決まり、集計 | 持たない（ファイル、時計、OS を触らない） |
| `openut-hublog` | `crates/openut-hublog/` | VIVE Hub のログの形: バイト列の解読、行の解析、出来事への変換、追記の追跡の判断、再生 | 持たない（ファイルの読み書きは、アプリが渡す） |
| `openut-anonymize` | `crates/openut-anonymize/` | ログの匿名化（L-1。Issue #8） | 持たない |

- 判定ロジック（ログの読み取り、状態の遷移、検出の規則）は、入出力から分ける（AGENTS.md）。そのため、判定を持つクレートは、ファイル・時計・OS の API を使わない。時刻は引数で受け取る。
- 通し版で足すクレート（`openut-dongle`、`openut-bridge`、`openut-driver`、`openut-space`、`openut-command`、`openut-runtime`）は、`walkthrough.md` の 1.7。`openut-driver` だけは、SteamVR に読み込ませる DLL（`cdylib`）で、`unsafe` を口の層のモジュールに閉じる（`walkthrough.md` の 1.3.3）。

## 5. 全段階の決まり

- **実機に送る命令は、設計で一覧にする**（D-13）。命令ごとに、何をするか、どこで確かめたか、危険、既定で送るかを書く。M1 が送る命令は**なし**（`m1-watcher.md` の 11 章）。M2 以降の一覧は Issue #6 の設計。再起動させる命令と書き込みの命令は、既定で禁止。
- **再生テスト**: 保存したログ（または M2 以降の記録）を時刻順に流して、検出を確かめる（W-8）。時刻は、ログに書かれた時刻だけで進める（`m1-watcher.md` の 10 章）。
- **個人の情報**: レポジトリに入れるログは、匿名化の道具（L-1）を通したものだけ。アプリが自分の保存場所に書くファイル（集計、アプリ自身のログ）には、シリアル番号が入りうるので、送る機能（L-4）は匿名化を通してから送る。
- **想定と違う入力で止まらない**: ログの行、機器からのデータが想定と違っても、`panic` せずに数えて読み続ける。

## 6. 調停役の決まり（M3）

VIVE Hub で起きた「始まらない」不具合は、次の 2 つが守られていないことで起きている（`findings-2026-11-27.md`）。M3 の調停役は、これを守る（R-2）。

1. ホストの Wi-Fi 情報は、ホストが替わるまで消さない。
2. クライアントに尋ねられて持っていなければ、ホストに問い合わせる。

M1 は、VIVE Hub がこれを守れなくなったこと（PC が Wi-Fi 情報を持たないまま、クライアントに尋ねられ続けること）を、ログから見つける（`m1-watcher.md` の 6 章の R1）。
