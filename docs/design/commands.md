# 実機に送る命令の一覧（第 2 版）

PC からドングルとトラッカーへ送りうるものを、分かる範囲ですべて並べた台帳（D-13、PRD の 11 章）。Issue #6 で作った最初の版に、通し版（Issue #57）の候補（8 章）と、試しの許可（6 章の 6）を足した。根拠の記号（S1〜S3、R1）と確かさの書き方は、`m2-dongle-protocol.md` の 1 章と同じ。

## 1. 決まり

- **この一覧にない命令は、どの段階でも送らない。** 送る機能を足すときは、先に設計の PR でこの一覧に足す。
- **既定で送るものは、ひとつもない**（この版の時点）。「既定で送る」に変えられるのは、オーナーが実機で確かめ、その結果（日付と Issue・PR）をこの一覧に書いたものだけ（D-13）。
- 「禁止」の命令は、設定でも有効にできない。**組み立てる関数を作らない**（5 章）。
- 「未確認」の命令は、既定で送らない（design.md の決まり）。
- 文字列の値に秘密（Wi-Fi のパスワード）や個人の情報（シリアル番号）が入る命令は、送ってよい段階になっても、値をログ・記録・画面に出さない。

### 危険の区分

| 区分 | 意味 | 扱い |
|---|---|---|
| **禁止・壊す** | 機器が動かなくなった記録がある | 送らない。作らない |
| **禁止・再起動** | 機器を再起動させる、電源を切る、書き換え用の起動に入る | 送らない（PRD 11 章）。作らない |
| **禁止・消す／書く** | ペアリング、地図、識別子、フラッシュ、ファームウェア、トラッカーの設定値を消す・書き換える | 送らない（PRD 11 章）。作らない |
| **状態を変える** | 追跡を始める、役割や形を変える、Wi-Fi 情報を渡す、その場の設定を変える。元に戻せる見込み | M3 以降。この一覧で確かさを上げ、オーナーの実機の確認のあとに有効にする |
| **問い合わせ** | 値を読むだけの見込み | 送るには、オーナーの了承が要る（DG-2）。副作用がないことは、どれも未確認 |
| **不明** | 意味が分からない | 禁止と同じ扱い |

## 2. M2 で送るもの

**なし。** M2 の道具（`m2-dongle-reader.md`）は、送る部分を持たない。

**読むために送らなければならないもの**は、いまの調べでは、次のとおり。

1. **ドングルの枠の状態、地図の状態、追跡の状態、姿勢**は、VIVE Hub が追跡を始めたあとなら、頼まずに届く見込み（`m2-dongle-protocol.md` の 5 章）。PC が何も送らないときに届くか（U-1）は、試し C で確かめる。
2. 届かない場合に、読むためだけに送りうる問い合わせの候補を、次の 3 つに絞った。**どれも M2 の最初の実装には入れない。** 試し C の結果を見て、要るものだけ、PM とオーナーの了承を得てから足す。

| 候補 | 命令 | 読めるもの | 要る場合 | 危険の見込み |
|---|---|---|---|---|
| Q1 | DC-04（`0x1E`、枠の状態の問い合わせ） | 5 つの枠の、ペアリングの有無と接続の状態 | `0x18` と `0x28` だけでは、接続と切断が分からないとき | 低い。VIVE Hub がペアリングの前に毎回送っている（S3）。副作用は未確認 |
| Q2 | DC-17（`0xFF`、ドングルの版の問い合わせ） | ドングルのファームウェアの版 | 版による違いを記録に残したいとき（U-10）。VIVE Hub のログで分かれば要らない | 低い。入力を確かめない命令と書かれている（S1）。副作用は未確認 |
| Q3 | TC-20（`P63:<key>`、SLAM の状態の問い合わせ） | 地図の状態、受け取った地図の有無、追跡の状態 | 地図の状態が頼まずに届かないとき（U-9） | 中くらい。無線でトラッカーまで届く。pyvut が定期的に送っている（S2）。副作用は未確認 |

3. **追跡を始めさせる命令（TC-01〜TC-11）は、問い合わせではない。** トラッカーの状態を変えるので、M2 では送らない。PC が送らないと姿勢が届かないと分かった場合の扱いは、PM に判断を仰ぐ（PR の「未解決」）。

## 4. トラッカーへの文字列の命令（TC。DC-01 で運ぶ）

文字列は 15 文字まで（S3 `settings-power.md` 3 章。HTC の側が長すぎる命令を断る）。トラッカーの Wi-Fi でつなぐ使い方では、同じ文字列を TCP で送る（S3）。OpenUT はドングルを使う。

## 5. USB で直接つないだトラッカーへの命令（UC。PID `0x06A3`、機能レポート）

## 6. 実装の決まり（M3 以降でコードにするときの形）

M2 のコードには、送る部分がない（`m2-dongle-reader.md` の 4 章）。M3 で送る部分を作るときは、次の形にする。

1. 命令を組み立てる関数は、この一覧の **「禁止」以外の ID ごとに 1 つ**だけ作る。生のバイト列や任意の文字列を送る関数は作らない。
2. 命令の表（ID、区分、確かさ、オーナーの確認の記録）をコードに持ち、送る前に必ず表を引く。表にない ID は送れない（組み立てる関数がないので、そもそも書けない）。
3. 「状態を変える」「問い合わせ」の命令は、利用者の設定で有効にしても、表の「オーナーの確認」が空なら送らない。
4. 送った命令は、ID、宛先（匿名の名前）、時刻を記録する。値が秘密の命令（TC-12）は、値を記録しない。
5. この一覧と、コードの表が食い違わないことを、テストで確かめる（一覧の ID の集合と、表の ID の集合が同じ）。
6. **試しの許可**（通し版。`walkthrough.md` の 3.1）: 3 の例外として、オーナーが確かめの手順の中で、実行のたびにコマンドの引数で切れ目の名前を書いたとき（例: `openut run --try K4`）だけ、8 章でその切れ目の候補に挙げた「状態を変える」「問い合わせ」の命令を、「オーナーの確認」が空でも送る。設定のファイルには書けない。許したことと、送った命令（ID、宛先の匿名の名前、時刻）を、アプリのログに書く。「禁止」の区分の命令は、組み立てる関数がないので、この許可でも送れない。

## 7. この一覧の直し方

- 命令を足す、区分を変える、確かさを上げるときは、設計の PR でこの文書を直す。
- オーナーが実機で確かめたときは、その命令の行の「確かさ」に「オーナーが確かめた（日付、Issue か PR の番号）」と書く。「既定」を変えるのは、そのあとの PR で行う。
- ファームウェアやドングルの版が変わったら、PM が見直しを依頼する（解析はトラッカーのファームウェア 1.0.999.178 のときのもの）。
