## 2. 全体の形

```
トラッカー ×3 ──(2.4GHz の無線)── ドングル ──(USB HID)── PC（いまは ViveTrackerServer.exe）
     │                                                        │
     └─ トラッカーどうしは、ホストが立てる Wi-Fi で地図を渡す ─┘（PC は Wi-Fi の名前とパスワードを仲立ちするだけ）
```

- ドングルは無線の中継役で、PC からの命令を、宛先のトラッカーへ文字列のまま届ける。トラッカーからの知らせ（文字列）と姿勢を、PC へまとめて返す。**解析（実機）**（S3 `mapbuild.md` 3 章、S2 `usb_protocol.md` 4・5 章）
- ドングルには 5 つの枠（スロット）があり、ペアリングしたトラッカーが入る。**解析（実機）**（S3 `pairing-and-status.md` 1・4 章）
- 地図の受け渡しは、トラッカーどうしの Wi-Fi で行い、USB を通らない。**解析**（S2 `usb_protocol.md` 9 章）。R1 の「始まらない問題」の仕組み（PC がホストから聞いた Wi-Fi 情報をクライアントに渡す）と合う。**ログと合う**

## 3. 機器の見つけ方

| 項目 | 内容 | 確かさ |
|---|---|---|
| ドングル | USB の VID `0x0BB4`（HTC）、PID `0x0350` | 解析（S1 `enums_usb.py`、S3） |
| USB で直接つないだトラッカー | VID `0x0BB4`、PID `0x06A3`。HID のインターフェースが 2 つ（0 と 1） | 解析（S1 `enums_usb.py`） |
| 使うインターフェース | ドングルのインターフェース 0。命令は機能レポート（feature report）、受け取りは入力レポート（input report。割り込み IN の 1 本、64 バイト）。ドングルには割り込み OUT がない | 解析（実機）（S3 `mapbuild.md` 3 章の取り込み） |
| HID の用途（usage page） | 書かれていない | 未確認。M2 の `list` で記録する |
| 入力レポートの長さ | 64 バイト | 解析（実機）（S3 `mapbuild.md`） |
| 古い型のドングル | Valve の VID `0x28DE`、PID `0x2101`（別の製品） | 解析（S1）。OpenUT では扱わない |

Windows では、HID の機器を `CreateFile` で開く。システムが専有する種類（キーボード、マウス、ペン、タッチ）以外は、共有で開ける。**公式**（S4 `hid-architecture.md`）。S5 の hidapi は、読み書きの権限と、読み書きの共有（`FILE_SHARE_READ | FILE_SHARE_WRITE`）で開く（S5 `open_device`）。

## 4. 枠組み（報告の形）

### 4.1 PC が送るもの（機能レポート）

- 64 バイトの機能レポート（先頭にレポート番号 0 を足して 65 バイト）。中身の先頭が命令の番号、次が長さ（データの長さ + 2）、そのあとにデータ、残りは 0。返事は、同じ番号の機能レポートを読んで受け取る（最大 10 回読み直し、先頭が同じ命令の番号になったものを返事とする）。**解析（実機）**（S2 `tracker_core.py` の `send_cmd`、S3 `pairing-and-status.md` 2 章、`mapbuild.md` 3 章）
- **送って読む（SET のあと GET）という形なので、2 つのプログラムが同時に命令を送ると、片方の返事をもう片方が読んでしまう**（解析からの推論）。「ドングルは同時に 1 つのプログラムしか扱えない」という前提（PRD の DG-3）の、少なくとも命令についての理由になる。

### 4.2 PC が受け取るもの（入力レポート）

先頭の 1 バイトが報告の種類。Windows の `ReadFile` は、レポート番号を使わない機器でも先頭に 0 を付けて返し、hidapi はそれを落として渡す（S5 の `read_timeout` の処理。S3 `pairing-and-status.md` 2 章の「先頭は 0、次が種類」も同じことを Windows の側から見ている）。以下の位置は、**先頭の 0 を落としたあと**で数える。

| 種類 | 意味 | 頻度 | 確かさ |
|---|---|---|---|
| `0x18` | ペアリング・ペアリング解除の知らせ（つながった・外れた） | まれ | 解析（実機）（S2、S3） |
| `0x1D`、`0x1E` | ドングルの枠の状態（問い合わせ `0x1E` の返事。`0x1D` は枠の振る舞いを変えた命令の返事） | 問い合わせたときだけ、と読める | 解析（S2、S3）。頼まずに届くかは未確認 |
| `0x28` | トラッカーからのデータ（文字列の知らせ、姿勢、ほか） | 毎秒約 244 件（地図を作っていたときの取り込み） | 解析（実機）（S3 `mapbuild.md`） |
| `0x29` | 不明 | 毎秒約 0.25 件 | 解析（実機）（S3 `mapbuild.md`）。中身は未確認 |

### 4.3 `0x28`（トラッカーからのデータ）の形

| 位置 | 大きさ | 中身 | 確かさ |
|---|---|---|---|
| 0 | 1 | `0x28` | 解析（実機） |
| 1〜2 | 2 | 通し番号（16 ビット、リトルエンディアン） | 解析（S2）。取りこぼしの見積もりに使える見込み（未確認） |
| 3〜8 | 6 | トラッカーの宛先（6 バイト）。うち 4〜8 の 5 バイトがトラッカーの識別子で、PC から命令を送るときの宛先と同じ。**この位置は `0x28` だけのもの**（`0x18` では位置が違う。4.7） | 解析（実機）（S3 `tracker_report.py`、`mapbuild.md` 3 章）。S2 は、2 バイト目の下位 4 ビットを枠の番号として使い、アドレスは「にせもの」と書いている。**無線のアドレスにあたるので、個人の情報として扱う**（AGENTS.md） |
| 9〜10 | 2 | 中身の種類（16 ビット）。`0x0101` = 文字列の知らせ、`0x0110` = 姿勢、それ以外 = 先頭の 1 バイトが種類のデータ | 解析（S2 `tracker_core.py`）。未確認 |
| 11 | 1 | 中身の長さ | 解析（S2） |
| 12〜 | 長さ分 | 中身 | 解析（S2） |

### 4.4 姿勢（中身の種類 `0x0110`）

中身は 37 バイト（`0x25`）か 39 バイト（`0x27`）。S3 は、HTC の側が 39 バイトと 50 バイト（`0x32`）で読み分けていると書いている。

| 位置（中身の先頭から） | 大きさ | 中身 | 確かさ |
|---|---|---|---|
| 0 | 1 | トラッカーの番号（0〜4） | 解析（S2） |
| 1 | 1 | ボタン、または電池（下の注） | 未確認（解析どうしが食い違う） |
| 2〜13 | 12 | 位置 x, y, z（32 ビット浮動小数点 ×3。メートル） | 解析（S2） |
| 14〜21 | 8 | 向き（16 ビット浮動小数点 ×4。**w, z, y, x の順**。ふつうの w, x, y, z に並べ替えて使う） | 解析（S2） |
| 22〜27 | 6 | 加速度（16 ビット浮動小数点 ×3） | 解析（S2） |
| 28〜35 | 8 | 角速度（16 ビット浮動小数点 ×4） | 解析（S2）。4 つ目の意味は未確認 |
| 36 | 1 | 追跡の状態（下の表） | 解析（S2）。番号は**ログと合う**（R1 の `Pose data - status: 2/3/4`） |
| 37〜 | 残り | 不明（電池などの周辺の値の見込み） | 未確認 |

追跡の状態の番号（S1 `enums_horusd_status.py`、S2 6.3 章）:

| 番号 | 意味 | VIVE Hub のログ |
|---|---|---|
| -1 | システムの準備ができていない | — |
| 0 | カメラの画像がまだない | — |
| 1 | 初期化されていない（位置合わせ待ち） | — |
| 2 | 追跡中 | `Pose data - status: 2` |
| 3 | 喪失（向きだけ有効） | `Pose data - status: 3` |
| 4 | 直前に喪失（位置は止まった値） | `Pose data - status: 4` |

**電池とボタンの注**: S3 の 2 つの記録が食い違う。`tracker_report.py` は「報告の 13 バイト目（中身の 1 バイト目）の最上位ビットが 0 なら、下位 7 ビット ×2 が電池の割合」、`pairing-and-status.md` 5.1 章は「周辺の値の 2 バイト目の最上位ビットが 0 なら、6 ビット目が充電中、下位 6 ビット ×2 が電池の割合。最上位ビットが 1 ならポゴピンの状態」と書き、その 2 バイトの位置は見つかっていないとも書いている。S2 は同じ 1 バイトをボタンの上位・下位として読む。**M2 では、このバイトを解釈せずに記録と表示（16 進）だけ行い**、VIVE Hub の画面の電池の割合と突き合わせて決める。

### 4.5 文字列の知らせ（中身の種類 `0x0101`）

トラッカーからの知らせは、短い ASCII の文字列。先頭の数文字で種類が決まる。S3 は、HTC の側が先頭の枠の番号の数字から読み始めると書いている（`pairing-and-status.md` 5.2 章）。数字が付くかどうかは未確認なので、読み取りは「先頭に数字が 1 つあれば枠の番号として外す」ことにする。

| 先頭 | 意味 | 個人の情報 | 確かさ |
|---|---|---|---|
| `NADS` | トラッカーのシリアル番号 | **含む** | 解析（S2、S3） |
| `NASS` | 出荷時のシリアル番号 | **含む** | 解析（S2、S3） |
| `NASI`、`NAPI` | SKU、基板の番号 | 機器を特定しうるので含むとみなす | 解析 |
| `NAV1` | ファームウェアの版 | 含まない | 解析 |
| `NARI` | 役割の番号 | 含まない | 解析 |
| `NAGN` | 動作の形（3 つの数） | 含まない | 解析。意味は未確認 |
| `NANA` | 名乗り（接続時） | 未確認 | 解析。意味は未確認 |
| `NADN`、`NADI` | 名前、機器の番号（推測） | 名前は利用者が付けうるので含むとみなす | 未確認 |
| `NAZZ` | 電源が切れる前の知らせ（S3）、機器情報の終わり（S2） | 含まない | 未確認（解析どうしが食い違う） |
| `MS<a>,<b>` | 地図の状態（`b` が下の地図の状態の番号） | 含まない | 解析（S2） |
| `LS<a>,<b>,<c>` / `LP...` | SLAM の状態・属性 | 含まない | 解析。意味は未確認 |
| `P61:<key>,<value>` | SLAM の状態の値（下の表の key） | 含まない | 解析（S2） |
| `P82:0:<code>` | SLAM の誤り（1100 カメラがない、1121・1122 カメラの異常、1200 IMU がない、1300 姿勢がない） | 含まない | 解析（S1 `enums_horusd_ack.py`）。M3 のクラッシュの検知（R-7）の手がかり |
| `WH<ssid>,<password>,<freq>` | ホストが立てた Wi-Fi の名前・パスワード・周波数 | **含む（秘密）** | 解析（S2 `tracker_core.py`） |
| `WS` | クライアントからの「Wi-Fi 情報をください」 | 含まない | 解析（S2 が、これを受けて Wi-Fi 情報を送り返す） |
| `WC<n>` | ホストの Wi-Fi につながったか（n > 0 でつながった） | 含まない | 解析（S2） |
| `APF`、`APR` | 電源オフ・リセットの知らせ | 含まない | 解析（S2） |
| `C...`、`c...` | 較正の値（何件かに分けて届く） | 機器ごとの値。含むとみなす | 解析（S2） |
| `DEC...` | 誤りの番号 | 含まない | 解析（S1）。意味は未確認 |

SLAM の状態の key（`P61`、S1 `enums_horusd_status.py`）: 0 送る準備、1 最初のファイルを受け取った、2 ホストの基本データを受け取った、3 ホストの地図を受け取った、4 いまの地図の番号、5 地図の状態、6 いまの追跡の状態。

地図の状態の番号（S1、S2 6.2 章）: 0 未確認、1 ある、2 ない、3 作り直した、4 保存した、5 保存に失敗、6 再利用に成功、7 再利用に失敗（特徴が違う）、8 再利用に失敗（特徴が少ない）、9 作り直しで静止待ち、10 作り直しで作成中。R1 の `map status: 6`（地図の再利用に成功）と番号が合う。**ログと合う**。R1 の `map state: 2` がどの値にあたるか（`P61:5` か、`LS` の 2 番目か）は未確認。

### 4.6 `0x18`（ペアリングの知らせ）と `0x1E`（枠の状態）

`0x18` は、`0x28` と頭の形が違う。S2 は、`0x28` 以外の受信（`0x18`、`0x1D`、`0x1E`、`0x29`）を、**共通の頭 4 バイト**（種類 1 バイト、長さ 1 バイト、不明 2 バイト）を除いてから読む（S2 `tracker_core.py` の `parse_incoming`。https://github.com/rocketmark/pyvut/blob/66f64a0/pyvut/tracker_core.py#L226-L231 ）。ペアリングの知らせは、その残りの先頭から、不明 1 バイト、外れたか 1 バイトを経て、宛先 6 バイトを読む（同じファイルの `do_loop` の `0x18` の読み。https://github.com/rocketmark/pyvut/blob/66f64a0/pyvut/tracker_core.py#L412-L422 ）。種類を位置 0 として数えると、**宛先は位置 6 から**になる。

- **直したこと**: この PR の第 1 版と第 2 版は、共通の頭を 2 バイト（種類と長さ）と数え、宛先を位置 4 からとしていた。誤りで、そのまま読むと、通知に固有の値（位置 4・5）が宛先に混ざる。PR #11 のレビュー 2 回目の指摘を受けて、S2 の上の 2 か所を読み直して直した（`parse_incoming` は、長さの次の 2 バイトを読み飛ばしてから残りを返す）。
- S3 は、HTC の側が、この知らせで「ドングルの枠の番号」を記録に出し、「つながった」を枠の番号で扱い、宛先を当てにしていないと書いている（S3 `pairing-and-status.md` 3.3 章）。枠の番号が知らせのどこにあるかは書かれていない。S2 が「不明」として読む位置 4 の 1 バイトがそれである可能性があるが、推測で、確かめていない（U-4）。

| 位置 | 大きさ | 中身 | 確かさ |
|---|---|---|---|
| 0 | 1 | `0x18` | 解析（実機）（S2、S3） |
| 1 | 1 | 長さ。S2 は、位置 4 から、この値の手前までを中身として読む（頭の 4 バイトを含めた長さとして使っている） | 解析（S2） |
| 2〜3 | 2 | 不明（S2 は読み飛ばす） | 未確認 |
| 4 | 1 | 不明（S2 は表示するだけ。枠の番号の可能性。上の注） | 未確認 |
| 5 | 1 | 外れたか（0 = つながった、1 = 外れた の見込み。ほかの値は不正として扱う） | 解析（S2）。値の意味は未確認 |
| 6〜11 | 6 | トラッカーの宛先。うち 7〜11 の 5 バイトが識別子（4.7） | 解析（S2 の読み方からの数え）。実機では未確認（U-4） |
| 12〜 | 残り | 不明 | 未確認 |

宛先の全体を読むには、長さ（位置 1）が 12 以上で、報告の長さ（64 バイト）を超えないことが要る。そうでない `0x18` は、解読では不正（`Malformed`）として扱う。

- `0x1E` の返事: 5 つの枠のそれぞれに 4 バイト（状態 1 バイト、接続の待ち時間 ms 2 バイト、印 1 バイト）。状態は 3 = 空き、5 = ペアリング済みでつながっていない、8 = つながっている、6 = 途中。印は、ビット 0 省電力、1 ペアリングの記録がある、2 ペアリングを受け付け中、3 接続中、4 無線がつながっている、5 IMU を USB へ送る、6 ファームウェアの更新中。**解析（実機）**（S3 4 章。値の意味は実機で確かめたとある）。5 つの記録が始まる位置: S2 の入力レポートの `0x1E` の読み（`parse_tracker_status`）を、上の 4 バイトの頭で数え直すと位置 9 になり、S3 が機能レポートの返事について書く「9 バイト目から」と同じ数になる。ただし、両者は経路（入力レポートか、機能レポートの返事か）が違い、S3 の数え方の起点も書かれていないので、未確認のまま扱う（第 1 版と第 2 版の「S2 と S3 で数え方が違う」は、頭を 2 バイトと数えた誤りから来ていた）。

### 4.7 トラッカーの宛先と識別子の位置（報告の種類ごと）

トラッカーの宛先は、報告の種類によって位置が違う。**解読（トラッカーの名前付け）と匿名化した書き出し（`m2-dongle-reader.md` の 6.2 と 8.4）は、この表だけを使い、位置をほかの場所に書かない。** 位置は、先頭の 0 を落としたあとで数える（4.2）。

| 報告 | 宛先（6 バイト） | 識別子（5 バイト。宛先の 2〜6 バイト目） | 枠の番号の推定（宛先の 2 バイト目の下位 4 ビット。S2 の使い方） | 根拠 | 確かさ |
|---|---|---|---|---|---|
| `0x28` | 3〜8 | 4〜8 | 4 の下位 4 ビット | S3 `tracker_report.py` の冒頭の説明、`mapbuild.md` 3 章（取り込み）。S2 `tracker_core.py` の `0x28` の読み | 解析（実機） |
| `0x18` | 6〜11 | 7〜11 | 7 の下位 4 ビット（`0x28` と同じ読み方を当てはめた推定。S2 も `0x18` の宛先に同じ読み方を使う） | S2 `tracker_core.py` の共通の頭の処理（L226–231。頭は 4 バイト）と `do_loop` の `0x18` の読み（L412–422。頭のあとの 2 バイトを経て宛先）（4.6） | 解析。位置は S2 の読み方からの数えで、実機では未確認（U-4） |
| `0x1D`、`0x1E`、`0x29`、そのほか | 決まっていない | — | — | どの解析にも書かれていない | 未確認。宛先が入っていても、位置が分からないので、解読では読まない（書き出しでは中身を落とす。`m2-dongle-reader.md` の 8.4） |

- 同じトラッカーなら、`0x18` の識別子と `0x28` の識別子は同じ 5 バイトになる見込み（未確認）。そうならない場合は、位置の読み違いか、宛先の形が違う。どちらかは試し C の記録で分かる（U-4）。
- 宛先のうち、識別子に入らない 1 バイト目（`0x28` の 3、`0x18` の 6）の意味は分かっていない（未確認）。無線のアドレスの一部でありうるので、識別子と同じく個人の情報として扱う。
- `0x18` の位置が実機で違っていた場合: 解読では、その知らせが、それまでの `0x28` のどの台とも合わない名前になる（`m2-dongle-reader.md` の 6.2 で数える）。共有用の書き出しでは、許した欄（`m2-dongle-reader.md` の 8.4.2）のほかは 0 にするので、位置を読み違えても元の宛先は書き出しに入らない。

## 6. PC が送るもの（まとめ）

すべての命令は `commands.md` に一覧にした。ここでは、VIVE Hub がふだん何を送っているかだけを書く。

- **ペアリング済みのトラッカーがつながると**、VIVE Hub は、そのトラッカーに、機器の番号（`ANI`）、`ATW`、カメラのフレームの速さ（`ACF60`）、時刻（`ATS`）、Wi-Fi の国（`Wc`）、`FW2`、追跡の形（クライアントなら `ATM11`）、自動スリープ（`pAS_TS0`）、Wi-Fi 情報（`Wf`、`Ws`、`Wt`、`Wp`）、`FW1` を送る。**解析（実機）**（S3 `mapbuild.md` 3 章の取り込み）。S2 は、役割（`ARI1`）、追跡の形、ホストかどうか（`ATH`、`AWH`）を送る。
- ホストにする命令は追跡の形の `ATM`（ホストは 20 か 21）。R1 の `Tracker (N) - switch to HOST mode.` にあたる見込み（未確認）。
- 空いた枠にペアリングを受け付けさせる命令（`0x1D`）と、その取り消しも、ふだんの手入れとして送っている。**解析（実機）**（S3）。
- つまり、**追跡を始めさせているのは PC**。トラッカーは、PC から追跡の形を受け取るまで、姿勢を出さない見込みが高い（S2 の流れ。未確認）。これが M2 の最大の不確かさで、`m2-dongle-reader.md` の 11 章の試しで確かめる。

## 10. この調べ書きの範囲外

- USB で直接つないだトラッカーとのやり取り（PID `0x06A3`）は、命令の一覧に載せただけ。トラッカー内のログの自前の取り出し（PRD の 6 章の注、L-3）の手がかりになる（`commands.md` の UC-02）。

- SteamVR のドライバーと VIVE Hub の名前付きパイプ（S3 `driver-pipes.md`）。M3 の設計で扱う。
